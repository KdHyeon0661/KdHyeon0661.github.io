# 커널 보안 및 권한 제어

## 왜 세분화된 권한 제어가 필요한가

전통적인 리눅스에서는 루트 사용자에게 모든 권한이 부여되었다. 이는 보안 위험이 될 수 있다. 예를 들어 웹 서버가 80번 포트를 열려면 루트 권한이 필요한데, 웹 서버에 취약점이 있으면 공격자가 시스템 전체를 장악할 수 있다.

이 문제를 해결하기 위해 **Linux Capabilities**는 루트 권한을 약 40개의 독립적인 권한 조각으로 나누고, **seccomp**는 프로세스가 호출할 수 있는 시스템 호출을 제한하며, **YAMA**는 프로세스 간 디버깅 접근을 통제한다.

---

## Linux Capabilities: 루트 권한의 세분화

### 주요 Capabilities

| Capability | 기능 | 사용 예 |
|------------|------|--------|
| `CAP_NET_BIND_SERVICE` | 1024 미만 포트 바인딩 | 웹 서버 (80, 443) |
| `CAP_NET_RAW` | raw 소켓 생성 | `ping`, `traceroute` |
| `CAP_SYS_TIME` | 시스템 시간 변경 | 시간 동기화 서비스 |
| `CAP_SYS_ADMIN` | 시스템 관리 권한 (루트와 유사) | **가능한 사용 금지** |
| `CAP_DAC_OVERRIDE` | 파일 권한 무시 | 보안 위험 높음 |

### Capabilities 확인 및 설정

```bash
# 현재 셸의 Capabilities 확인
capsh --print

# 파일에 Capability 부여 (예: ping)
sudo setcap cap_net_raw+ep /bin/ping

# 부여된 Capability 확인
getcap /bin/ping
```

- `+ep` : Effective와 Permitted 집합에 추가
- `+i` : Inheritable 집합에 추가

### 실전 예제: 웹 서버에 최소 권한 부여

```bash
# 80번 포트 바인딩 권한만 부여
sudo setcap cap_net_bind_service=+ep /usr/local/bin/myweb
```

이제 웹 서버는 루트로 실행하지 않아도 80번 포트를 사용할 수 있다.

## seccomp: 시스템 호출 제한

seccomp는 프로세스가 호출할 수 있는 시스템 호출을 제한하는 커널 보안 기능이다.

### 동작 모드

- **STRICT 모드**: `read`, `write`, `exit`, `sigreturn`만 허용 (너무 제한적)
- **FILTER 모드**: BPF 프로그램으로 시스템 호출을 정밀 제어 (실무에서 사용)

### Docker에서 seccomp 적용

```bash
# 기본 seccomp 프로파일 사용
docker run --rm --security-opt seccomp=default nginx
```

### 허용 목록(Allowlist) 설계

효과적인 seccomp 정책은 **허용 목록** 방식으로 설계한다. 필요한 시스템 호출만 허용하고 나머지는 모두 차단한다.

```bash
# 애플리케이션의 시스템 호출 분석
strace -f -o trace.log /usr/local/bin/myapp
```

## ptrace 제어: YAMA

ptrace는 프로세스 디버깅 도구(`strace`, `gdb` 등)의 핵심이지만, 악용될 경우 보안 위협이 될 수 있다. YAMA는 ptrace 접근을 제한하는 리눅스 보안 모듈이다.

### YAMA 설정

```bash
# 현재 정책 확인
cat /proc/sys/kernel/yama/ptrace_scope

# 권장 설정 (동일 사용자만 ptrace 허용)
echo 1 | sudo tee /proc/sys/kernel/yama/ptrace_scope

# 영구 설정
echo "kernel.yama.ptrace_scope=1" | sudo tee /etc/sysctl.d/10-ptrace.conf
sudo sysctl --system
```

### YAMA 정책 수준

| 값 | 의미 |
|----|------|
| 0 | 모든 ptrace 허용 (개발 환경) |
| 1 | 동일 사용자 프로세스만 허용 (권장) |
| 2 | 자식 프로세스만 허용 |
| 3 | 모든 ptrace 금지 |

## systemd 보안 속성: 통합 보안 관리

systemd는 서비스 유닛 파일에서 다양한 보안 속성을 설정할 수 있다.

### 보안 강화된 서비스 유닛 예제

```ini
# /etc/systemd/system/myapp.service
[Unit]
Description=보안 강화 애플리케이션

[Service]
ExecStart=/usr/local/bin/myapp
User=myapp
Group=myapp

# Capabilities: 80번 포트 바인딩만 허용
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
AmbientCapabilities=CAP_NET_BIND_SERVICE

# 권한 상승 방지
NoNewPrivileges=yes

# 파일 시스템 보호
ProtectSystem=strict          # 시스템 디렉터리 읽기 전용
ProtectHome=yes               # 홈 디렉터리 접근 차단
PrivateTmp=yes                # 독립적인 /tmp
PrivateDevices=yes            # 장치 노드 접근 제한

# 시스템 호출 필터 (허용 목록)
SystemCallFilter=@system-service @network-io

# 네트워크 주소 패밀리 제한
RestrictAddressFamilies=AF_INET AF_INET6

[Install]
WantedBy=multi-user.target
```

### 서비스 보안 수준 확인

```bash
systemd-analyze security myapp.service
```

### 임시 제한으로 테스트 실행

```bash
systemd-run -t \
  -p MemoryMax=200M \
  -p CPUQuota=50% \
  -p CapabilityBoundingSet=CAP_NET_BIND_SERVICE \
  -p NoNewPrivileges=yes \
  /usr/local/bin/myapp
```

## 보안 효과의 수학적 모델

시스템 호출 허용 개수를 $N$이라고 하자. 각 시스템 호출에 취약점이 존재할 확률을 $p_i$라 할 때, 보안 위반 가능성은 다음과 같이 근사할 수 있다.

$$
\text{보안 위반 가능성} \approx 1 - \prod_{i=1}^{N} (1 - p_i)
$$

허용 시스템 호출 수 $N$을 줄이고, 위험도 $p_i$가 높은 호출(`ptrace`, `keyctl`, `mount` 등)을 제거하면 보안 위험은 급격히 감소한다.

## 문제 해결 가이드

| 증상 | 가능한 원인 | 해결 |
|------|------------|------|
| 80번 포트 바인딩 실패 | `CAP_NET_BIND_SERVICE` 부족 | `setcap cap_net_bind_service+ep /경로/바이너리` |
| 파일 쓰기 실패 | `ProtectSystem=strict`로 루트 읽기 전용 | `ReadWritePaths=/허용/경로` 추가 |
| 디버깅 안 됨 | `ptrace_scope` 제한 | 운영 환경은 유지, 개발 노드에서만 완화 |
| `ping` 명령 실패 | `CAP_NET_RAW` 필요 | `setcap cap_net_raw+ep /bin/ping` |

## 결론

리눅스 커널 보안은 세 가지 핵심 기술의 조합으로 구현된다.

- **Capabilities**: 루트 권한을 세분화하여 필요한 최소 권한만 부여한다.
- **seccomp**: 허용된 시스템 호출만 실행하도록 제한한다.
- **YAMA**: 프로세스 간 디버깅 접근을 통제한다.

**운영 시 권장 사항**:
- 웹 서버 등 1024 미만 포트를 사용하는 서비스는 `CAP_NET_BIND_SERVICE`만 부여하고 루트로 실행하지 않는다.
- systemd 서비스 유닛에 `NoNewPrivileges=yes`, `ProtectSystem=strict`, `PrivateTmp=yes` 등을 기본으로 적용한다.
- `systemd-analyze security`로 서비스의 보안 수준을 정기적으로 점검한다.
- 개발 환경과 운영 환경의 보안 정책을 분리한다 (운영은 더 엄격하게).

보안은 단일 도구가 아니라 체계적인 접근 방식이다. 각 서비스에 필요한 최소 권한을 정량화하고, 지속적으로 모니터링하며 조정하는 습관이 중요하다.
