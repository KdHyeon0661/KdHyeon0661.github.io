# 작업 예약과 서비스 관리

## 왜 작업 예약이 중요한가

리눅스 시스템 운영에서 자동화는 필수다. 정기적인 백업, 로그 회전, 인증서 갱신 같은 반복 작업은 사람이 매일 실행할 수 없다. 또한 서비스는 예기치 않게 중단될 수 있으며, 이에 대한 복구도 자동화되어야 한다. 이를 위해 리눅스는 세 가지 핵심 도구를 제공한다.

* **cron / systemd timer**: 주기적으로 실행해야 하는 작업
* **at**: 한 번만 실행할 작업
* **systemctl**: 서비스(데몬)의 수명주기 관리

---

## cron: 전통적인 주기 작업 예약

### crontab 기본

cron은 시스템 전역 또는 사용자별로 작업을 예약하는 도구다. 각 사용자는 `crontab -e` 명령으로 자신의 작업 목록을 편집할 수 있다.

```bash
crontab -e          # 편집
crontab -l          # 목록 보기
crontab -r          # 전체 삭제
```

crontab 파일의 한 줄은 다음 형식을 따른다.

```
분 시 일 월 요일 명령
```

각 필드에 들어갈 수 있는 값은 다음과 같다.

| 필드 | 범위 | 비고 |
|------|------|------|
| 분 | 0–59 | |
| 시 | 0–23 | |
| 일 | 1–31 | |
| 월 | 1–12 | |
| 요일 | 0–7 | 0과 7은 일요일 |

**특수 표현**
* `*` : 모든 값
* `,` : 여러 값 (예: `1,15`)
* `-` : 범위 (예: `1-5`)
* `/` : 간격 (예: `*/5`는 5분마다)

**자주 쓰는 별칭**
```crontab
@reboot   명령     # 부팅 시 한 번
@daily    명령     # 매일 00:00
@hourly   명령     # 매시 정각
```

### 실제 예제

```crontab
# 매일 02:30에 백업 실행
30 2 * * * /usr/local/bin/backup.sh

# 5분마다 상태 기록
*/5 * * * * /usr/local/bin/status_log.sh

# 매주 일요일 23:00에 정리
0 23 * * 0 /home/user/cleanup.sh
```

### cron 실행 시 주의점

cron은 사용자 로그인 환경을 그대로 가져오지 않는다. `PATH`가 짧고, 쉘 설정 파일(`.bashrc` 등)을 읽지 않으므로 **절대 경로**를 사용하고 필요한 환경 변수를 명시해야 한다.

```crontab
# 상단에 환경 설정 가능 (일부 구현)
SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

# 작업
0 2 * * * /usr/local/bin/backup.sh >> /var/log/backup.log 2>&1
```

스크립트 내에서도 경로를 명시적으로 설정하는 것이 안전하다.

### 동시 실행 방지 (flock)

같은 작업이 여러 번 겹쳐 실행되면 문제가 생길 수 있다. `flock`을 사용해 잠금을 걸면 중복 실행을 방지할 수 있다.

```crontab
*/5 * * * * /usr/bin/flock -n /var/lock/myjob.lock /usr/local/bin/myjob.sh
```

`-n` 옵션은 잠금을 얻지 못하면 즉시 종료한다.

### 시스템 cron 디렉터리

`/etc/crontab`과 `/etc/cron.d/` 디렉터리에는 **사용자 필드**가 추가된다.

```
분 시 일 월 요일 사용자 명령
```

`/etc/cron.hourly`, `/etc/cron.daily` 등은 `run-parts`로 실행되는 표준 디렉터리다. 여기에 실행 권한이 있는 스크립트를 넣으면 주기적으로 실행된다.

### anacron: 놓친 작업 보상

노트북처럼 항상 켜져 있지 않은 시스템에서는 예정된 시간에 cron이 실행되지 않을 수 있다. anacron은 다음 부팅 시 놓친 작업을 보상 실행해준다.

```ini
# /etc/anacrontab
1    10    cron.daily    run-parts /etc/cron.daily
7    25    cron.weekly   run-parts /etc/cron.weekly
```

첫 번째 숫자는 주기(일), 두 번째는 지연 시간(분)이다.

## at: 일회성 작업 예약

`at` 명령은 특정 시간에 단 한 번 실행할 작업을 예약한다.

```bash
echo "reboot" | at 03:00
echo "systemctl restart myapp" | at now + 90 minutes
```

`atq`로 대기 중인 작업 목록, `atrm <jobid>`로 취소할 수 있다.

`atd` 서비스가 실행 중이어야 한다.

```bash
sudo systemctl status atd
```

## systemd timer: cron의 현대적 대안

systemd는 `timer` 유닛을 통해 주기 작업을 관리할 수 있다. `cron`보다 로깅, 의존성, 보안 측면에서 더 강력하다.

### 기본 구조

타이머는 `.timer` 파일과 실행할 `.service` 파일로 구성된다.

**서비스 유닛** (`/etc/systemd/system/backup.service`)

```ini
[Unit]
Description=Daily backup

[Service]
Type=oneshot
ExecStart=/usr/local/bin/backup.sh
User=backup
```

**타이머 유닛** (`/etc/systemd/system/backup.timer`)

```ini
[Unit]
Description=Daily backup timer

[Timer]
OnCalendar=daily
Persistent=true
RandomizedDelaySec=5m

[Install]
WantedBy=timers.target
```

`OnCalendar`은 cron과 유사한 표현을 지원한다.

```ini
OnCalendar=*-*-* 02:00:00     # 매일 02:00
OnCalendar=Mon..Fri 09:00      # 평일 09:00
OnCalendar=*-*-01 00:15        # 매월 1일 00:15
```

활성화 및 상태 확인:

```bash
sudo systemctl enable --now backup.timer
systemctl list-timers
journalctl -u backup.service
```

### cron과 비교

| 항목 | cron | systemd timer |
|------|------|---------------|
| 로그 | 별도 리다이렉션 필요 | journalctl로 통합 |
| 의존성 | 제한적 | `After=`, `Wants=` 등 풍부 |
| 놓친 실행 보상 | anacron 필요 | `Persistent=true` |
| 랜덤 분산 | 직접 구현 | `RandomizedDelaySec` |
| 보안 격리 | 제한적 | `ProtectSystem`, `PrivateTmp` 등 |

## systemctl: 서비스 관리

systemd 환경에서 서비스는 `systemctl` 명령으로 제어한다.

```bash
sudo systemctl start nginx
sudo systemctl stop nginx
sudo systemctl restart nginx
sudo systemctl reload nginx    # 설정만 다시 읽기
sudo systemctl status nginx
sudo systemctl enable nginx    # 부팅 시 자동 시작
sudo systemctl disable nginx
```

### 서비스 유닛 파일 예시

```ini
# /etc/systemd/system/myapp.service

[Unit]
Description=My Application
After=network.target

[Service]
Type=simple
User=myapp
Group=myapp
ExecStart=/usr/local/bin/myapp
Restart=on-failure
RestartSec=5s

[Install]
WantedBy=multi-user.target
```

- `Restart=on-failure` : 비정상 종료 시 자동 재시작
- `RestartSec=5s` : 재시작 전 5초 대기

### 유닛 파일 수정 (override)

기본 유닛 파일을 직접 수정하는 대신 오버라이드 디렉터리를 사용한다.

```bash
sudo systemctl edit myapp.service
```

이 명령은 `/etc/systemd/system/myapp.service.d/override.conf`를 열어주며, 여기에 추가 설정을 적으면 된다. 수정 후에는 반드시 `daemon-reload`를 실행한다.

```bash
sudo systemctl daemon-reload
sudo systemctl restart myapp
```

## 실전 시나리오

### 시나리오 1: 안전한 백업 작업 (cron + flock)

```crontab
SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

0 2 * * * /usr/bin/flock -n /var/lock/backup.lock /usr/local/bin/backup.sh >> /var/log/backup.log 2>&1
```

백업 스크립트 `backup.sh`:

```bash
#!/bin/bash
set -euo pipefail
rsync -a /data/ /backup/data/
echo "$(date): backup completed"
```

### 시나리오 2: systemd timer로 교체

서비스 유닛 (`/etc/systemd/system/backup.service`):

```ini
[Unit]
Description=Nightly backup

[Service]
Type=oneshot
ExecStart=/usr/local/bin/backup.sh
User=backup
```

타이머 유닛 (`/etc/systemd/system/backup.timer`):

```ini
[Unit]
Description=Nightly backup timer

[Timer]
OnCalendar=*-*-* 02:00:00
Persistent=true
RandomizedDelaySec=10m

[Install]
WantedBy=timers.target
```

### 시나리오 3: 일회성 야간 재부팅

```bash
echo "systemctl reboot" | at 03:00
atq
```

### 시나리오 4: 서비스 자동 재시작

`myapp.service`에 이미 `Restart=on-failure`가 있으므로, 장애 발생 시 자동으로 재시작된다. 로그 확인:

```bash
journalctl -u myapp -f
```

## 문제 해결

### cron이 실행되지 않는 경우

1. **절대 경로 사용** – cron은 PATH가 제한적이므로 명령어 전체 경로를 적는다.
2. **권한 확인** – 스크립트에 실행 권한이 있는지, 사용자가 작업을 등록할 권한이 있는지.
3. **로그 확인** – 메일이 설정되어 있으면 작업 결과가 메일로 전송된다. 표준 출력/에러를 파일로 리다이렉트하는 것이 좋다.
4. **SELinux/AppArmor** – 보안 정책이 cron 작업을 막을 수 있다.

### systemd timer가 실행되지 않는 경우

```bash
systemctl list-timers               # 다음 실행 시간 확인
systemctl status myjob.timer        # 타이머 상태
journalctl -u myjob.service -b      # 서비스 로그
```

타이머가 `enabled`이고 `timers.target`에 의해 시작되었는지 확인한다.

### 서비스가 재시작 루프에 빠질 때

`RestartSec`을 늘리고, `StartLimitBurst`를 조정한다.

```ini
[Service]
Restart=on-failure
RestartSec=30s
StartLimitInterval=5min
StartLimitBurst=3
```

## 핵심 명령어 요약표

| 작업 | 명령어 / 파일 |
|------|----------------|
| 사용자 cron 편집 | `crontab -e` |
| 사용자 cron 목록 | `crontab -l` |
| 시스템 cron 설정 | `/etc/crontab`, `/etc/cron.d/*` |
| anacron 설정 | `/etc/anacrontab` |
| at 작업 예약 | `at`, `atq`, `atrm` |
| 서비스 제어 | `systemctl start/stop/restart/status` |
| 부팅 시 자동 시작 | `systemctl enable/disable` |
| 서비스 로그 | `journalctl -u 서비스` |
| timer 목록 | `systemctl list-timers` |
| timer 활성화 | `systemctl enable --now 이름.timer` |

## 결론

리눅스에서 작업 예약과 서비스 관리는 시스템 안정성과 자동화의 핵심이다. 전통적인 cron과 at은 간단한 주기/일회성 작업에 여전히 유용하지만, systemd timer와 서비스 유닛은 더 강력한 로깅, 의존성 제어, 보안 격리를 제공한다.

**선택 기준**
* 단순한 주기 작업 → cron (빠르고 직관적)
* 고급 로깅, 의존성, 보안이 필요 → systemd timer
* 한 번 실행 → at

**운영 팁**
* 모든 작업은 절대 경로를 사용하고, 필요한 환경 변수를 명시한다.
* 작업 결과를 로그 파일로 남기거나 journal을 활용한다.
* 중복 실행 방지를 위해 `flock`을 사용한다.
* systemd 서비스는 `Restart=` 정책을 설정해 장애 복구를 자동화한다.
* 정기 작업의 설정 파일은 버전 관리(Git)로 관리한다.

이러한 패턴을 적용하면 시스템 운영의 신뢰성과 효율성을 크게 높일 수 있다.
