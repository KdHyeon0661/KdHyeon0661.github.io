# 부팅과 서비스 관리

## 시스템 부팅의 전체 흐름

리눅스 시스템이 켜지는 순간부터 사용자가 로그인하기까지는 여러 단계를 거친다. 이 과정을 이해하면 시스템 문제를 해결하고 최적화할 수 있다.

### 1. 펌웨어 단계 (BIOS / UEFI)
전원을 켜면 CPU는 펌웨어(BIOS 또는 UEFI)를 실행한다. 하드웨어를 초기화하고 부팅할 장치(디스크, USB 등)를 선택한다. UEFI 환경에서는 ESP(EFI 시스템 파티션)에서 부트로더를 찾아 실행한다.

### 2. 부트로더 단계 (GRUB)
GRUB는 커널 이미지와 initramfs(초기 RAM 파일시스템)를 메모리에 로드한다. 부팅 메뉴를 보여주고, 사용자가 커널 파라미터를 임시로 수정할 수 있게 한다.

### 3. 커널과 initramfs 단계
커널이 실행되면서 하드웨어 드라이버, 메모리 관리, 프로세스 관리 등 핵심 기능을 초기화한다. initramfs는 실제 루트 파일시스템(예: 암호화된 파티션이나 LVM)을 마운트할 수 있도록 임시 환경을 제공한다.

### 4. init 프로세스 단계 (systemd)
루트 파일시스템이 마운트되면 커널은 `systemd`(PID 1)를 실행한다. systemd는 의존성에 따라 서비스들을 병렬로 시작하고, 시스템을 최종 상태(target)로 끌어올린다.

### 5. 로그인 단계
TTY 콘솔, SSH 데몬, 또는 그래픽 디스플레이 매니저(GDM, LightDM 등)를 통해 사용자 로그인 환경이 제공된다.

## GRUB 부트로더 실무

### 임시 부팅 옵션 추가
GRUB 메뉴에서 원하는 항목을 선택한 뒤 `e` 키를 누르면 편집 모드로 들어간다. `linux`로 시작하는 줄 끝에 필요한 파라미터를 추가하고 `Ctrl+x`로 부팅한다.

예를 들어 복구 모드로 부팅하려면:
```text
linux /boot/vmlinuz-... root=UUID=... ro systemd.unit=rescue.target
```

### GRUB 설정 재생성
커널을 새로 설치하거나 GRUB 설정을 변경한 경우 설정 파일을 다시 만들어야 한다.

**Debian/Ubuntu 계열**:
```bash
sudo update-grub
```

**RHEL/Fedora 계열 (UEFI)**:
```bash
sudo grub2-mkconfig -o /boot/efi/EFI/redhat/grub.cfg
```

## 자주 사용하는 커널 파라미터

| 파라미터 | 용도 |
|----------|------|
| `systemd.unit=rescue.target` | 단일 사용자 모드(복구)로 부팅 |
| `systemd.unit=emergency.target` | 최소한의 셸만 제공하는 긴급 모드 |
| `rd.break` | initramfs 단계에서 셸 진입 (루트 비밀번호 재설정 등) |
| `selinux=0` | SELinux 일시 비활성화 (문제 진단용) |

## initramfs 재생성

하드웨어 드라이버나 파일시스템 모듈을 변경한 경우 initramfs를 다시 만들어야 할 수 있다.

**Debian/Ubuntu**:
```bash
sudo update-initramfs -u -k all
```

**RHEL/Fedora**:
```bash
sudo dracut -f
```

## systemd 핵심 개념

### 유닛(Unit)의 종류
- `.service` : 데몬, 서비스
- `.socket` : 소켓 활성화 (요청 시 서비스 시작)
- `.timer` : 예약 실행 (cron 대체)
- `.path` : 파일 변경 감지 시 실행
- `.mount` / `.automount` : 파일시스템 마운트
- `.target` : 실행 그룹 (런레벨 개념)

### 서비스 유닛 예시
`/etc/systemd/system/myapp.service`:
```ini
[Unit]
Description=My Application
After=network.target

[Service]
User=myapp
Group=myapp
ExecStart=/opt/myapp/bin/myapp
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

- `After` : 실행 순서 (의존성 아님, 순서만 지정)
- `Wants` / `Requires` : 실행 의존성 (`Requires`는 실패 시 이 서비스도 실패)
- `Restart` : 비정상 종료 시 재시작 정책

### 유닛 파일 관리 명령
```bash
sudo systemctl daemon-reload          # 유닛 파일 변경 후 적용
sudo systemctl enable --now myapp     # 부팅 시 자동 시작 + 즉시 시작
sudo systemctl status myapp           # 상태 확인
journalctl -u myapp -f                # 로그 실시간 확인
```

### 드롭인(override)으로 설정 확장
패키지에서 제공하는 기본 유닛을 직접 수정하지 말고 `systemctl edit`로 오버라이드 파일을 만든다.

```bash
sudo systemctl edit nginx
```
```ini
[Service]
Environment="NGINX_CONF=/etc/nginx/nginx.conf"
```
변경 후 `systemctl daemon-reload`와 재시작이 필요하다.

## 타겟과 런레벨

| 런레벨 | systemd 타겟 | 설명 |
|--------|--------------|------|
| 0 | `poweroff.target` | 종료 |
| 1 | `rescue.target` | 단일 사용자 복구 모드 |
| 3 | `multi-user.target` | CLI 다중 사용자 (서버 기본) |
| 5 | `graphical.target` | GUI 포함 (데스크톱) |
| 6 | `reboot.target` | 재부팅 |

```bash
systemctl get-default                     # 현재 기본 타겟 확인
sudo systemctl set-default multi-user.target   # 기본을 CLI로 변경
sudo systemctl isolate rescue.target      # 지금 바로 복구 모드로 전환
```

## 부팅 성능 분석

```bash
systemd-analyze time                      # 전체 부팅 시간
systemd-analyze blame                     # 각 유닛별 소요 시간 (느린 순)
systemd-analyze critical-chain            # 크리티컬 경로 추적
```

부팅이 느리면 `blame` 결과에서 오래 걸리는 유닛을 확인하고, 불필요한 서비스를 비활성화하거나 `After` 의존성을 조정한다.

## 고급 유닛 활용 (간략)

### 소켓 활성화: 서비스를 요청 시에만 실행
`socket` 유닛과 `service` 유닛을 함께 만든다. 클라이언트가 소켓에 연결하면 systemd가 서비스를 시작한다.

### 타이머 유닛: cron 대체
```bash
# 서비스 유닛 (nightly-backup.service)
[Service]
Type=oneshot
ExecStart=/usr/local/bin/backup.sh

# 타이머 유닛 (nightly-backup.timer)
[Timer]
OnCalendar=02:30
RandomizedDelaySec=5m
Persistent=true
```
```bash
sudo systemctl enable --now nightly-backup.timer
systemctl list-timers
```

### 패스 유닛: 파일 변경 감지
`path` 유닛으로 설정 파일 변경 시 서비스를 자동으로 재로드할 수 있다.

## 사용자 서비스와 linger

사용자별로 systemd 서비스를 실행할 수도 있다. 기본적으로 사용자가 로그아웃하면 사용자 서비스도 종료되지만, `linger`를 활성화하면 로그아웃 후에도 계속 실행된다.

```bash
systemctl --user enable --now mytool.service
sudo loginctl enable-linger username
journalctl --user -u mytool -f
```

## 부팅 실패 복구 시나리오

### Rescue / Emergency 모드 진입
GRUB 편집 모드에서 `linux` 줄 끝에 다음을 추가한다.
```text
systemd.unit=rescue.target
```
또는
```text
systemd.unit=emergency.target
```

Rescue 모드에서 루트 파일시스템을 읽기/쓰기로 재마운트:
```bash
mount -o remount,rw /
```

### 루트 비밀번호 분실
GRUB 편집 모드에서 `linux` 줄 끝에 `rd.break`를 추가하고 부팅한다.
```bash
mount -o remount,rw /sysroot
chroot /sysroot
passwd
touch /.autorelabel   # SELinux 사용 시
exit
exit
```

### 서비스 디버깅
```bash
systemctl status myapp
journalctl -u myapp -b -e
systemctl cat myapp
systemctl show myapp | grep -E 'ExecStart|User|WorkingDirectory'
```
자주 실패하는 원인: 경로 오류, 권한 부족, 환경 변수 누락, 과도한 보안 옵션.

## SysVinit 호환 (레거시)

일부 구형 시스템이나 스크립트는 여전히 `service`와 `chkconfig` 명령을 사용한다.
```bash
sudo service ssh restart
sudo chkconfig httpd on
```
현대 배포판에서는 대부분 내부적으로 systemctl로 연결된다.

## 핵심 명령어 요약

| 작업 | 명령어 |
|------|--------|
| 서비스 시작/중지/재시작 | `systemctl start\|stop\|restart NAME` |
| 부팅 시 자동 시작 설정 | `systemctl enable\|disable NAME` |
| 서비스 상태 확인 | `systemctl status NAME` |
| 로그 확인 | `journalctl -u NAME -f` |
| 유닛 파일 재로드 | `systemctl daemon-reload` |
| 유닛 오버라이드 편집 | `systemctl edit NAME` |
| 기본 타겟 확인/변경 | `systemctl get-default`, `set-default multi-user.target` |
| 부팅 분석 | `systemd-analyze time\|blame\|critical-chain` |
| 사용자 서비스 | `systemctl --user ...`, `loginctl enable-linger USER` |

## 결론

리눅스 부팅 과정은 펌웨어 → GRUB → 커널/initramfs → systemd → 로그인으로 이어진다. systemd는 현대 리눅스의 핵심으로, 서비스 의존성 관리, 병렬 시작, 다양한 유닛 타입, 보안 강화, 자원 제한 등을 제공한다.

문제 발생 시 GRUB 편집으로 복구 모드에 진입하고, `systemctl status`와 `journalctl`로 원인을 파악한다. 부팅 성능이 느리면 `systemd-analyze blame`으로 병목을 찾는다.

서비스 유닛을 작성할 때는 `Restart=on-failure`, `ProtectSystem=full`, `PrivateTmp` 등의 옵션으로 안정성과 보안을 높이고, 패키지 업데이트에 덮어쓰이지 않도록 드롭인 방식을 활용한다. 이러한 기초를 바탕으로 체계적으로 시스템을 관리할 수 있다.
