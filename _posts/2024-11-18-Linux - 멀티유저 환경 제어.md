# 멀티유저 환경 제어

## 리소스 제어의 계층 구조

리눅스 시스템에서 여러 사용자가 동시에 작업할 때, 자원(CPU, 메모리, 파일 개수, 프로세스 수 등)을 적절히 제한하지 않으면 한 사용자의 과도한 사용이 시스템 전체에 영향을 줄 수 있다.  
리소스 제어는 크게 세 가지 계층으로 나뉜다.

1. **systemd 유닛(Unit) 수준**  
   - 가장 강력한 제어 방식으로, 서비스나 사용자 세션 단위로 cgroup을 통해 CPU, 메모리, 파일 핸들 등을 제한한다.
   - 운영 환경의 서비스에 적용하는 최우선 수단이다.

2. **PAM limits**  
   - `/etc/security/limits.conf`와 그 하위 디렉터리(`limits.d`)를 통해 로그인 시점에 적용되는 제한이다.
   - 로그인 셸이나 SSH 세션 등 PAM을 거치는 모든 사용자에게 적용된다.

3. **셸 내부 `ulimit`**  
   - 현재 셸 세션에서만 임시로 적용되는 제한이다.
   - 자식 프로세스에 상속되지만, 로그아웃하면 사라진다.

이 계층들은 **soft ≤ hard** 규칙을 따른다. soft limit은 사용자가 조정할 수 있는 범위이며, hard limit은 root만 높일 수 있는 상한선이다.

## `ulimit`: 현재 세션의 즉시 제한

`ulimit` 명령은 현재 셸과 그 하위 프로세스에 적용되는 리소스 제한을 확인하거나 변경한다.  
변경은 현재 세션에만 적용되며, 새 로그인 시 다시 초기화된다.

```bash
# 모든 제한 확인
ulimit -a

# 열 수 있는 파일 개수(soft) 확인
ulimit -n

# soft limit을 4096으로 변경
ulimit -n 4096

# hard limit과 soft limit을 함께 보고 싶을 때
ulimit -Sn
ulimit -Hn
```

자주 사용하는 항목:

| 항목 | 옵션 | 설명 |
|------|------|------|
| 열린 파일 | `-n` | 파일 디스크립터 최대 개수 |
| 프로세스 수 | `-u` | 사용자당 최대 프로세스/스레드 수 |
| 파일 크기 | `-f` | 생성할 수 있는 파일 최대 크기(블록 단위) |
| CPU 시간 | `-t` | 프로세스의 최대 CPU 시간(초) |

실행 중인 프로세스의 현재 제한은 `/proc/<PID>/limits`에서 확인할 수 있다.

```bash
cat /proc/$$/limits       # 현재 셸 자신의 제한
```

또한 이미 실행 중인 프로세스의 제한을 `prlimit` 명령으로 변경할 수 있다.

```bash
# PID 1234의 열린 파일 제한을 soft=4096, hard=8192로 변경
sudo prlimit --pid 1234 --nofile=4096:8192
```

## PAM limits: 로그인 시 영구 적용

사용자가 로그인할 때마다 자동으로 적용되는 제한은 `/etc/security/limits.conf`와 `/etc/security/limits.d/*.conf`에 설정한다.  
이 파일들은 PAM의 `pam_limits.so` 모듈에 의해 읽힌다.

구문 형식:

```conf
<도메인>  <type>  <item>  <value>
```

- **도메인**: 사용자 이름, `@그룹명`, 또는 `*`(모든 사용자)
- **type**: `soft`(사용자가 변경 가능), `hard`(변경 불가, root만), `-`(soft와 hard 모두)
- **item**: `nofile`(파일 개수), `nproc`(프로세스 수), `maxlogins`(동시 로그인 수), `fsize`(파일 크기) 등
- **value**: 제한 값

예시:

```conf
# 사용자 devkim: 파일 개수 soft=2048, hard=4096
devkim   soft  nofile  2048
devkim   hard  nofile  4096

# 모든 사용자의 프로세스 수 제한
*        soft  nproc   1024
*        hard  nproc   2048

# developers 그룹 멤버는 코어 덤프 금지
@developers hard  core   0

# 동시 로그인 수 제한 (SSH 등)
*        hard  maxlogins  10
```

**중요**: 이 제한이 적용되려면 로그인 경로가 PAM을 거쳐야 한다.  
- 일반 로그인(`login`), SSH(`sshd`), `su`, `sudo` 등 각각의 PAM 설정 파일(`/etc/pam.d/`)에 `session required pam_limits.so` 라인이 포함되어 있어야 한다.  
- systemd로 직접 실행되는 서비스(예: `systemctl start myservice`)는 PAM을 거치지 않으므로 `limits.conf`가 적용되지 않는다. 이런 경우 서비스 유닛에 직접 제한을 설정해야 한다.

적용 확인은 재로그인 후 `ulimit -n` 등을 실행해보면 된다.

## systemd와 cgroups: 서비스·세션 단위 제어

운영 환경에서 가장 확실한 리소스 제어 방법은 systemd의 서비스 유닛에 직접 제한을 설정하는 것이다.  
cgroups v2를 통해 CPU, 메모리, 파일 핸들, 프로세스 수 등을 그룹 단위로 제한한다.

### 서비스 유닛에 제한 추가

`/etc/systemd/system/myapp.service` 파일 내 `[Service]` 섹션에 다음과 같이 옵션을 추가한다.

```ini
[Service]
ExecStart=/opt/myapp/bin/app

# 파일 디스크립터 수
LimitNOFILE=65535

# 프로세스/스레드 총 수
TasksMax=4096

# 메모리 상한 (예: 2GB)
MemoryMax=2G

# CPU 사용량 제한 (한 코어의 20%)
CPUQuota=20%

# 스왑 사용 제한
MemorySwapMax=0

# 실패 시 재시작
Restart=on-failure
```

변경 후 적용:

```bash
sudo systemctl daemon-reload
sudo systemctl restart myapp
```

현재 적용된 값을 확인하려면 `systemctl show myapp -p LimitNOFILE,MemoryCurrent,CPUUsageNSec` 등을 사용한다.

### 시스템 전체 기본값 설정

모든 서비스에 적용될 기본값은 `/etc/systemd/system.conf`와 `/etc/systemd/user.conf`에 정의할 수 있다.

```ini
DefaultLimitNOFILE=65535
DefaultTasksMax=12288
```

변경 후:

```bash
sudo systemctl daemon-reexec
```

### 사용자 세션 제어

사용자가 로그인하면 systemd는 `user-<UID>.slice`라는 cgroup 슬라이스를 생성한다. 이 슬라이스에 대한 제한도 가능하다.

```bash
# 현재 사용자 슬라이스 상태
systemctl status user-$(id -u).slice
```

임시로 제한을 걸고 명령을 실행하려면 `systemd-run`을 사용한다.

```bash
# 메모리 1GB, CPU 50% 제한된 셸 실행
systemd-run --user --scope -p MemoryMax=1G -p CPUQuota=50% bash
```

### 로그아웃 후에도 사용자 서비스 유지 (linger)

사용자가 로그아웃해도 systemd 사용자 서비스가 계속 실행되게 하려면 `enable-linger`를 사용한다.

```bash
sudo loginctl enable-linger devkim
sudo -u devkim systemctl --user enable --now my-timer.service
```

## 디스크 사용 제한: Quota

멀티유저 환경에서는 디스크 공간을 개별 사용자별로 제한할 필요가 있다. 리눅스의 디스크 쿼터(quota) 기능이 이를 지원한다.

### 쿼터 활성화

먼저 파일시스템 마운트 옵션에 `usrquota`(사용자) 또는 `grpquota`(그룹)를 추가한다.  
`/etc/fstab` 예시:

```fstab
UUID=xxxx-xxxx  /home  ext4  defaults,usrquota,grpquota  0  2
```

재마운트:

```bash
sudo mount -o remount /home
```

### 쿼터 초기화 및 활성화

```bash
# 쿼터 데이터베이스 생성
sudo quotacheck -cum /home

# 쿼터 시스템 활성화
sudo quotaon /home
```

### 사용자별 제한 설정

```bash
sudo edquota devkim
```

편집 화면에서 블록(디스크 사용량)과 inode(파일 개수)의 soft/hard 제한을 설정할 수 있다.  
설정 후 `quota -u devkim`으로 확인한다.

```bash
# 전체 보고서
repquota -a
```

## 세션 및 사용자 관리

멀티유저 환경에서 누가 로그인해 있는지, 어떤 작업을 하고 있는지 확인하는 것도 중요하다.

```bash
# 현재 로그인 사용자
who -uH
w

# 최근 로그인 기록
last -n 20
last reboot
```

systemd 환경에서는 `loginctl` 명령으로 세션을 관리할 수 있다.

```bash
# 전체 세션 목록
loginctl list-sessions

# 특정 세션 강제 종료
loginctl terminate-session <SID>

# 사용자별 linger 상태 확인
loginctl show-user devkim
```

## 트러블슈팅 흐름

### "Too many open files" 오류 발생

1. 현재 프로세스의 제한 확인  
   `cat /proc/<PID>/limits | grep "open files"`

2. 서비스가 systemd로 관리된다면 유닛 파일 확인  
   `systemctl show <서비스> -p LimitNOFILE`

3. PAM limits가 적용되는지 확인  
   로그인 셸이라면 `ulimit -n`으로 확인하고, 필요시 `/etc/security/limits.conf` 수정

4. systemd 서비스라면 유닛 파일에 `LimitNOFILE=` 추가

### "Resource temporarily unavailable" (프로세스 수 초과)

- `ulimit -u` 또는 `limits.conf`의 `nproc` 확인
- systemd 서비스라면 `TasksMax=` 값 확인

### 디스크 쿼터 초과

- `quota -u 사용자`로 현재 사용량 확인
- `edquota`로 soft/hard 조정, 또는 유예 기간(grace) 확인

## 실전 시나리오

### 시나리오 1: 데이터베이스 서버의 파일 디스크립터 부족

```bash
# 문제 확인
cat /proc/$(pidof postgres)/limits | grep "open files"

# 해결: 서비스 유닛 오버라이드
sudo systemctl edit postgresql
```

오버라이드 파일 내용:

```ini
[Service]
LimitNOFILE=262144
```

적용:

```bash
sudo systemctl daemon-reload
sudo systemctl restart postgresql
```

### 시나리오 2: 빌드 서버 사용자의 과도한 병렬 작업 제한

`/etc/security/limits.d/50-buildfarm.conf`:

```conf
@buildfarm hard nproc   2000
@buildfarm hard maxlogins 20
```

### 시나리오 3: 연구 계정 디스크 사용 제한

```bash
sudo edquota researcher1
# 블록 soft/hard 설정 (예: 5GB / 10GB)
sudo repquota -a | grep researcher1
```

## 핵심 명령어 요약표

| 작업 | 명령어 / 파일 |
|------|----------------|
| 현재 세션 제한 확인 | `ulimit -a` |
| 실행 중 프로세스 제한 확인 | `cat /proc/<PID>/limits` |
| 프로세스 제한 변경 | `prlimit --pid <PID> --nofile=soft:hard` |
| PAM limits 설정 | `/etc/security/limits.conf`, `/etc/security/limits.d/*.conf` |
| 서비스 유닛 제한 | `LimitNOFILE=`, `TasksMax=`, `MemoryMax=`, `CPUQuota=` |
| systemd 전역 기본값 | `/etc/systemd/system.conf` |
| 임시 제한 실행 | `systemd-run --user --scope -p MemoryMax=1G bash` |
| 사용자 세션 관리 | `loginctl list-sessions`, `loginctl terminate-session` |
| 쿼터 설정 | `quotacheck`, `quotaon`, `edquota`, `quota`, `repquota` |

## 결론

멀티유저 환경에서 자원 제어는 시스템 안정성과 공정성을 보장하는 핵심 요소다.  
- **일회성 확인과 조정**에는 `ulimit`과 `prlimit`을 활용한다.  
- **로그인 시 항상 적용되는 정책**은 PAM limits(`limits.conf`)를 사용한다.  
- **서비스나 사용자 세션의 확실한 제한**은 systemd 유닛 옵션(`LimitNOFILE`, `MemoryMax` 등)을 통해 cgroup 레벨에서 설정한다.  
- **디스크 공간**은 쿼터로 사용자별로 제한한다.

각 계층의 특성을 이해하고 적절히 조합하면, 여러 사용자가 함께 사용하는 리눅스 시스템도 안정적으로 운영할 수 있다. 설정 후에는 반드시 재로그인 또는 서비스 재시작으로 적용을 확인하고, 필요시 `systemctl daemon-reload`나 `sysctl --system`을 잊지 말자.
