# 네트워크 디버깅과 방화벽 설정

## 체계적인 접근이 필요한 이유

네트워크 문제는 원인을 찾기 어렵고, 증상만으로는 어느 계층에서 문제가 발생했는지 알기 어렵다. 따라서 **계층별로 차근차근 점검하는 방식**이 효과적이다.  
일반적으로 다음 순서로 확인한다.

1. **링크/주소 계층** : 네트워크 인터페이스, IP 주소, 게이트웨이 연결  
2. **경로 계층** : 라우팅 테이블, ARP 테이블, 외부 통신 가능 여부  
3. **소켓 계층** : 서비스가 포트를 열고 있는지, 바인딩 주소 확인  
4. **방화벽 계층** : 호스트 방화벽, 클라우드 보안 그룹 등  
5. **애플리케이션 계층** : DNS, HTTP, TLS 등  

---

## 기본 건강검진

문제가 생겼을 때 가장 먼저 실행할 몇 가지 명령어다.

```bash
ip -br a                  # 인터페이스와 IP 주소 간단히 보기
ip r                      # 라우팅 테이블 (기본 게이트웨이 포함)
ping -c 3 8.8.8.8         # 외부 연결 확인
ping -c 3 $(ip r | awk '/default/ {print $3}')  # 게이트웨이 확인
ss -tuln                  # 열려 있는 포트와 리스닝 서비스 확인
resolvectl status || cat /etc/resolv.conf   # DNS 설정 확인
```

이 단계에서 외부 연결이 안 되면 게이트웨이나 인터페이스 설정을, 특정 포트 접속이 안 되면 서비스나 방화벽을 의심한다.

---

## 계층별 진단

### 링크 및 주소 계층
```bash
ip link show               # 인터페이스 상태 (UP/DOWN)
ip -br a                   # IP 주소 확인
```

- 인터페이스가 `DOWN`이면 `ip link set eth0 up`으로 활성화
- IP 주소가 없으면 `ip addr add 192.168.1.10/24 dev eth0` 등으로 추가

### 라우팅 계층
```bash
ip r get 8.8.8.8           # 특정 목적지로 가는 경로 확인
ip neigh                   # ARP 테이블 (이웃 장치)
```

- 기본 게이트웨이가 없으면 `ip r add default via 192.168.1.1 dev eth0` 추가
- ARP 테이블에 게이트웨이 MAC이 없으면 로컬 통신 문제

### DNS 계층
```bash
dig +short example.com
getent hosts example.com   # /etc/hosts, DNS 순서로 해석
```

- `dig @1.1.1.1 example.com`으로 공개 DNS와 비교하여 로컬 DNS 문제 확인

### 소켓/서비스 계층
```bash
ss -tulnp | grep :80       # 80번 포트를 리스닝하는 프로세스 확인
systemctl status nginx     # 서비스 상태 확인
```

- 리스닝 주소가 `127.0.0.1`이면 외부에서 접근 불가 → 설정에서 `0.0.0.0`으로 변경 필요

### 경로 추적
```bash
traceroute -n 8.8.8.8
mtr -rwzbc 100 8.8.8.8     # mtr 패키지 설치 필요
```

- 특정 홉에서 패킷 손실이 시작되면 해당 구간 문제 가능성

### 애플리케이션 계층
```bash
curl -vI https://example.com
nc -vz example.com 443
```

- `curl`로 HTTP 응답, TLS 핸드셰이크까지 확인 가능
- `nc`로 TCP 연결 가능 여부만 확인

## MTU 문제 진단

증상: 작은 패킷은 되지만 큰 파일 전송 시 끊김, VPN 사용 시 특정 사이트 접속 불가.

```bash
# MTU 1500 경로 테스트 (IPv4: 1472바이트 페이로드)
ping -M do -s 1472 8.8.8.8
```

실패하면 MTU 값을 낮춰본다.

```bash
ip link set dev eth0 mtu 1400
```

---

## 패킷 캡처 (tcpdump)

확실한 증거를 얻고 싶다면 패킷을 직접 본다.

```bash
sudo tcpdump -i any port 443 -c 50 -w https.pcap
```

- SYN 패킷은 보내는데 SYN/ACK 응답이 없으면 방화벽이나 경로 문제
- TLS 핸드셰이크 중단은 MTU나 중간 장비(DPI) 의심

## 방화벽 설정

### UFW (Ubuntu 기본)

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 22/tcp
sudo ufw allow 80,443/tcp
sudo ufw enable
sudo ufw status verbose
```

### firewalld (RHEL/Fedora)

```bash
sudo systemctl enable --now firewalld
sudo firewall-cmd --zone=public --add-service=http --permanent
sudo firewall-cmd --reload
sudo firewall-cmd --list-all
```

### nftables (현대 리눅스 기본)

최소한의 방화벽 예시:

```bash
sudo nft add table inet filter
sudo nft add chain inet filter input { type filter hook input priority 0 \; policy drop \; }
sudo nft add rule inet filter input iif lo accept
sudo nft add rule inet filter input ct state established,related accept
sudo nft add rule inet filter input tcp dport {22,80,443} accept
sudo nft add rule inet filter input ip protocol icmp accept
```

규칙 저장: `sudo sh -c 'nft list ruleset > /etc/nftables.conf'`

## 실전 시나리오

### 1. 외부에서 HTTPS 접속 불가

1. `ss -tulnp | grep :443` → 서비스 리스닝 확인
2. `curl -v https://127.0.0.1 --insecure` → 로컬 접속 테스트
3. `sudo ufw status` 또는 `sudo nft list ruleset` → 방화벽 확인
4. 클라우드 보안 그룹에서 443 포트 허용되었는지 확인
5. `tcpdump -i eth0 port 443` → SYN/ACK 흐름 확인

### 2. 외부 접속은 느리고 내부는 빠름

- `mtr`로 경로별 지연과 손실 확인
- MTU 테스트 (`ping -M do -s 1472 대상`)
- 로드밸런서나 CDN 구간 문제일 수 있음

| firewalld | `firewall-cmd --add-service` |

## 결론

네트워크 문제는 계층적 사고와 적절한 도구로 해결할 수 있다. 기본 점검(`ip`, `ping`, `ss`)으로 대략적인 범위를 좁히고, `traceroute`, `curl`, `tcpdump`로 상세를 확인한다. 방화벽은 **기본 차단 + 필요한 서비스만 허용** 원칙으로 설정하고, 환경(Ubuntu는 UFW, RHEL은 firewalld, 직접 nftables)에 맞게 관리한다.

처음에는 모든 명령어를 외울 필요 없이, 문제 상황에서 어떤 계층을 점검할지 순서를 기억하는 것이 중요하다. 사내 공유 문서에 체크리스트를 만들어 두면 더 빠르게 대응할 수 있다.
