# 권한 관리 기초와 고급 설정

## 파일과 디렉터리의 권한 의미

리눅스 권한은 **소유자(owner)**, **그룹(group)**, **기타(others)** 세 범주에 대해 **읽기(r)**, **쓰기(w)**, **실행(x)** 권한을 부여한다. 파일과 디렉터리에서 권한의 의미가 다르므로 반드시 구분해야 한다.

| 대상 | r | w | x |
|------|---|---|---|
| 파일 | 내용 읽기 | 내용 수정/삭제 | 실행 가능 여부 |
| 디렉터리 | 목록 조회(`ls`) | 파일/디렉터리 생성·삭제·이름 변경 | 디렉터리 진입(`cd`) 및 탐색 |

디렉터리에 실행(x) 권한이 없으면 `cd`로 진입할 수 없다. 읽기(r) 권한만 있어도 정확한 파일명을 알면 접근할 수 있지만, 실행 권한도 함께 있어야 한다.

권한은 기호(`rwxr-x---`) 또는 8진수로 표현한다. 8진수는 각 권한을 비트 합으로 나타낸다.

$$
\text{perm} = 4\cdot I(r) + 2\cdot I(w) + 1\cdot I(x)
$$

예를 들어 `rwxr-x---`는 소유자=7, 그룹=5, 기타=0이므로 `750`이다.

```bash
# 경로 전체의 권한 확인 (어느 디렉터리에서 탐색이 막히는지 파악)
namei -l /path/to/some_dir
```

## chmod: 권한 변경

`chmod`는 숫자 표기법과 기호 표기법을 모두 지원한다.

### 숫자 표기법
```bash
chmod 755 script.sh        # rwxr-xr-x
chmod 640 secret.txt       # rw-r-----
```

### 기호 표기법
```bash
chmod u+x,g-w,o= file.sh   # 소유자 실행 추가, 그룹 쓰기 제거, 기타 권한 없음
chmod -R u=rwX,go-rwx data/   # X: 디렉터리나 이미 실행 권한이 있는 파일에만 실행 부여
```

### 특수 비트
- setuid (4) : 실행 시 소유자 권한으로 실행
- setgid (2) : 디렉터리에서 생성되는 파일의 그룹 상속
- sticky (1) : 디렉터리 내 파일 소유자만 삭제 가능

```bash
chmod 4755 /usr/bin/passwd   # setuid
chmod 2755 /shared/          # setgid
chmod 1777 /tmp              # sticky
```

## chown, chgrp: 소유자와 그룹 변경

```bash
sudo chown user:group file.txt
sudo chown -R www-data:www-data /var/www
sudo chgrp developers /srv/repo
```

## umask: 기본 권한 설정

새로 생성되는 파일과 디렉터리의 기본 권한은 각각 666과 777에서 umask 값을 뺀 값이다.

$$
\text{최종 권한} = \text{기본값} - \text{umask}
$$

```bash
umask           # 현재 확인 (예: 0022)
umask 027       # 파일 640, 디렉터리 750
```

## ACL: 세분화된 권한 관리

기본 user/group/others만으로는 부족할 때 개별 사용자나 그룹에 권한을 추가할 수 있다.

```bash
# 패키지 설치 (Ubuntu)
sudo apt install -y acl

# 파일에 john 사용자에게 읽기 권한 부여
setfacl -m u:john:r-- file.txt

# 디렉터리 재귀 적용 (rwX: 디렉터리에는 실행 부여, 파일은 원래 실행 권한 있을 때만)
setfacl -Rm u:john:rwX /data/project/

# 디렉터리에 기본 ACL 설정 (새 파일/디렉터리에 상속)
setfacl -m d:g:devs:rwX /data/project

# ACL 확인
getfacl file.txt

# ACL 제거
setfacl -x u:john file.txt
setfacl -b file.txt
```

ACL의 **mask**는 추가 권한의 상한선이다. `chmod`를 실행하면 mask가 변경될 수 있으므로 주의해야 한다.

## Linux Capabilities: setuid 대안

setuid는 루트의 모든 권한을 부여하는 위험이 있다. 필요한 최소 권한만 부여하는 **Capabilities**를 사용하는 것이 좋다.

```bash
# 1024 미만 포트 바인딩 허용
sudo setcap cap_net_bind_service=+ep /usr/local/bin/myserver

# 확인
getcap /usr/local/bin/myserver
```

## chattr: 확장 파일 속성

일반 권한과 별도로 파일을 변경 불가나 추가 전용으로 설정할 수 있다.

```bash
sudo chattr +i /important/config.yml   # 변경 불가 (루트도 수정/삭제 불가)
sudo chattr -i /important/config.yml
sudo chattr +a /var/log/secure         # 추가 전용 (로그 무결성)

lsattr /important/config.yml
```

## sudo, su, passwd, id: 계정 권한 승격

```bash
id                        # 현재 사용자 정보
sudo -u www-data ls /var/www   # 다른 사용자 권한으로 실행
sudo -i                   # 루트 셸로 전환
su -                      # 루트 환경으로 전환 (대상 사용자 비밀번호 필요)
passwd                    # 자신의 비밀번호 변경
sudo passwd -l testuser   # 계정 잠금
```

`sudoers` 파일은 `visudo`로 안전하게 편집한다.

```
%deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart myapp
```

## SELinux와 AppArmor 개념

기본 권한(DAC) 위에 정책 기반 접근 제어(MAC)를 적용한다.

**SELinux** (RHEL 계열)
```bash
getenforce
sestatus
# 거부 로그 확인
sudo ausearch -m avc -ts recent
# 일시적 허용 모드 (문제 파악용)
sudo setenforce 0
```

**AppArmor** (Ubuntu 등)
```bash
sudo aa-status
sudo aa-logprof   # 거부 로그 기반 정책 학습
```

권한과 ACL이 정상인데 접근이 안 된다면 SELinux/AppArmor를 의심해야 한다.

## 실전 시나리오

### 팀 공유 디렉터리: setgid + 기본 ACL

모든 파일이 `devs` 그룹 소유가 되고, 그룹 읽기/쓰기 권한이 상속되도록 설정한다.

```bash
sudo mkdir -p /srv/project
sudo chgrp -R devs /srv/project
sudo chmod 2775 /srv/project                     # setgid
setfacl -m d:g:devs:rwx /srv/project             # 기본 ACL
```

### 80번 포트 바인딩: Capabilities

```bash
sudo setcap cap_net_bind_service=+ep /usr/local/bin/myserver
```

### 로그 무결성: append-only

```bash
sudo chattr +a /var/log/myapp.log
```

### 권한 문제 진단 루틴

```bash
namei -l /srv/app/config.yaml            # 경로 탐색 권한 확인
getfacl /srv/app/config.yaml              # ACL 확인
getenforce && sudo ausearch -m avc -ts recent   # SELinux 확인
```

## 핵심 명령어 요약

|------|--------|
| 기본 권한 | `chmod`, `chown`, `chgrp`, `umask` |

| AppArmor | `aa-status`, `aa-logprof` |

## 결론

리눅스 권한은 **기본 퍼미션 → ACL → Capabilities → MAC(SELinux/AppArmor)** 의 계층 구조로 이해해야 한다. 상위 계층은 하위 계층의 제한을 넘어설 수 없으며, 실제 접근은 모든 계층의 허가가 필요하다.

문제 해결 시에는 `namei -l`로 경로 탐색 권한을 확인하고, `getfacl`로 ACL과 마스크를 점검한 뒤, SELinux/AppArmor 로그를 확인하는 순서로 접근하는 것이 효과적이다. **최소 권한 원칙**을 지키면서도 팀 협업과 서비스 운영에 필요한 권한을 적절히 조합하여 안전하고 효율적인 시스템을 구성하길 바란다.
