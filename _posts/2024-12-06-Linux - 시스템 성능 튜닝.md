# 시스템 성능 튜닝 기초

## 커널 파라미터 (sysctl) 기초

리눅스 커널은 다양한 동작을 조정할 수 있는 파라미터를 제공한다. `sysctl` 명령으로 실시간으로 확인하고 변경할 수 있으며, 영구적인 설정은 `/etc/sysctl.d/` 디렉터리에 파일로 저장한다.

### 현재 값 확인 및 임시 변경

```bash
# 현재 값 확인
sysctl net.ipv4.tcp_tw_reuse
sysctl vm.swappiness

# 임시 변경 (재부팅 시 초기화)
sudo sysctl -w net.ipv4.tcp_tw_reuse=1
sudo sysctl -w vm.swappiness=10
```

### 영구 변경

`/etc/sysctl.d/99-tuning.conf` 파일 생성:

```conf
net.ipv4.tcp_tw_reuse = 1
net.ipv4.tcp_fin_timeout = 30
vm.swappiness = 10
vm.vfs_cache_pressure = 50
fs.file-max = 2097152
net.core.somaxconn = 4096
```

적용:
```bash
sudo sysctl --system
```

### 주요 커널 파라미터

| 파라미터 | 설명 | 권장값 (서버) |
|---------|------|--------------|
| `net.core.somaxconn` | TCP 백로그 큐 크기 | 4096 이상 |
| `net.ipv4.tcp_tw_reuse` | TIME_WAIT 소켓 재사용 | 1 |
| `net.ipv4.tcp_fin_timeout` | FIN-WAIT-2 상태 유지 시간(초) | 30 |
| `vm.swappiness` | 스왑 사용 정도 (0~100) | 10 (SSD), 60 (기본) |
| `vm.vfs_cache_pressure` | inode/dentry 캐시 회수 압박 (100 기본) | 50 (캐시 유지) |
| `fs.file-max` | 시스템 전체 최대 파일 핸들 수 | 2097152 |
| `kernel.pid_max` | 최대 PID 수 | 4194304 |
| `net.ipv4.ip_local_port_range` | 로컬 포트 범위 | 1024 65000 |

## 파일시스템 튜닝 옵션

파일시스템 성능은 마운트 옵션에 크게 영향을 받는다. `/etc/fstab`에서 영구적으로 설정하거나 `mount -o remount`로 임시 변경할 수 있다.

### 자주 사용하는 마운트 옵션

| 옵션 | 설명 | 권장 |
|------|------|------|
| `noatime` | 파일 접근 시간 기록 안 함 (읽기 성능 ↑) | 데이터 파티션 권장 |
| `relatime` | 접근 시간을 최적화하여 기록 (기본값) | 시스템 파티션 |
| `nodiratime` | 디렉터리 접근 시간 기록 안 함 | `noatime`에 포함 |
| `discard` | 삭제된 블록을 SSD에 즉시 TRIM (성능 영향) | 주기적 `fstrim` 권장 |
| `barrier=0` | 저널 쓰기 장벽 비활성화 (성능 ↑, 안정성 ↓) | 배터리 백업 장치에서 고려 |
| `data=writeback` | ext4에서 데이터 저널링 비활성화 (성능 ↑) | 안정성보다 속도가 중요할 때 |

### ext4 특화 옵션

```bash
# /etc/fstab 예시
UUID=xxx /data ext4 defaults,noatime,data=ordered 0 2
UUID=yyy /ssd  ext4 defaults,noatime,discard 0 2
```

- `data=ordered` : 기본, 메타데이터만 저널, 데이터는 먼저 기록
- `data=writeback` : 성능↑, 충돌 시 데이터 손상 가능
- `noatime` : 대부분의 서버에 적용하면 좋음

### XFS 특화 옵션

```bash
UUID=zzz /data xfs defaults,noatime,inode64,attr2 0 2
```

- `inode64` : 64비트 inode 사용 (대용량 파일시스템)
- `attr2` : 확장 속성 최적화
- `largeio` : 대규모 I/O 최적화

### 마운트 옵션 변경 (실시간)

```bash
# 읽기 전용으로 재마운트
sudo mount -o remount,ro /data
# 옵션 추가
sudo mount -o remount,noatime /data
```

## I/O 스케줄러 변경

I/O 스케줄러는 디스크 요청의 처리 순서를 결정한다. 현대 리눅스는 다중 큐 블록 계층(mq-deadline, kyber, bfq)을 사용하며, 장치별로 스케줄러를 선택할 수 있다.

### 현재 스케줄러 확인

```bash
cat /sys/block/sda/queue/scheduler
# 출력 예: [mq-deadline] kyber bfq
```

대괄호 안의 항목이 현재 활성화된 스케줄러다.

### 임시 변경 (재부팅 시 초기화)

```bash
echo bfq | sudo tee /sys/block/sda/queue/scheduler
```

### 영구 변경 (커널 부트 파라미터)

`/etc/default/grub`의 `GRUB_CMDLINE_LINUX`에 추가:

```bash
GRUB_CMDLINE_LINUX="elevator=bfq"
```

업데이트:
```bash
sudo update-grub   # Debian/Ubuntu
sudo grub2-mkconfig -o /boot/grub2/grub.cfg  # RHEL/Fedora
```

### 주요 I/O 스케줄러 특징

| 스케줄러 | 특징 | 권장 사용처 |
|----------|------|-------------|
| `mq-deadline` | 지연 시간 보장, 기본값 | 일반 서버, SSD |
| `kyber` | 낮은 지연 시간, 동시성 조절 | 빠른 NVMe, 고성능 환경 |
| `bfq` | 공정한 대역폭 분배 | 데스크톱, 멀티태스킹 |

### SSD와 HDD의 차이

- **HDD**: 물리적 탐색 시간이 중요 → `mq-deadline` 또는 `bfq`가 적합
- **SSD**: 탐색 시간 없음 → `mq-deadline` 또는 `kyber`가 일반적
- **NVMe**: 매우 높은 처리량 → `kyber` 권장

## 튜닝 적용 시 주의사항

1. **변경 전 백업**: `/etc/sysctl.d/`, `/etc/fstab`, `/etc/default/grub` 수정 전에 백업
2. **단일 변경 후 테스트**: 한 번에 여러 파라미터를 변경하지 말고, 영향 관찰
3. **부팅 가능성 확인**: fstab 수정 후 `sudo mount -a`로 구문 검증
4. **모니터링 도구 활용**: `iostat -x`, `vmstat 1`, `perf` 등으로 효과 측정

## 핵심 명령어 요약표

| 작업 | 명령어 / 파일 |
|------|--------------|
| sysctl 확인 | `sysctl -a | grep tcp` |
| sysctl 임시 변경 | `sudo sysctl -w net.ipv4.tcp_tw_reuse=1` |
| sysctl 영구 설정 | `/etc/sysctl.d/*.conf` |
| fstab 편집 | `/etc/fstab`, `sudo mount -a` |
| 마운트 옵션 재적용 | `sudo mount -o remount,noatime /data` |
| I/O 스케줄러 확인 | `cat /sys/block/sda/queue/scheduler` |
| I/O 스케줄러 변경 | `echo bfq > /sys/block/sda/queue/scheduler` |
| 부트 파라미터 추가 | `/etc/default/grub`, `update-grub` |

## 결론

시스템 성능 튜닝은 하드웨어와 워크로드에 따라 적절한 값을 찾아가는 과정이다.

- **커널 파라미터**는 네트워크, 메모리, 파일 핸들 등 시스템 전반의 동작을 조정한다.
- **파일시스템 튜닝**은 `noatime`, 적절한 저널 모드, 디스크 타입에 맞는 마운트 옵션으로 I/O 효율을 높인다.
- **I/O 스케줄러**는 디스크 특성(HDD/SSD/NVMe)에 맞게 선택하여 응답성과 처리량을 최적화한다.

처음부터 많은 값을 변경하기보다는, 관찰(모니터링) → 가설 → 변경 → 검증의 단계로 접근하는 것이 바람직하다. 작은 변경이라도 재부팅 후 영향을 충분히 확인하고, 필요시 원복할 수 있도록 기록을 남기는 습관을 들이자.
