# SELinux & AppArmor 보안 모듈

## 왜 MAC이 필요한가? DAC에서 MAC으로

전통적인 리눅스 접근 제어(DAC)는 파일 소유자와 권한(`rwx`, `setuid` 등)에 기반한다. 하지만 루트 프로세스가 공격당하면 시스템 전체가 위험해질 수 있다.

**MAC(Mandatory Access Control)**은 “기본적으로 허용하지 않음(deny by default)” 원칙을 적용한다. 프로세스, 파일, 포트 등에 라벨(정책)을 부여하여 **루트 권한도 제약**한다.

- 최소 권한 원칙(Least Privilege)
- 허용 목록 기반 접근(Allow-listing)
- 정책과 로깅을 통한 가시성 확보

---

## SELinux 핵심 개념

### 동작 모드

```bash
getenforce           # Enforcing, Permissive, Disabled
setenforce 0         # Permissive (일시, 로그만 기록)
setenforce 1         # Enforcing (복귀)
```

- **Enforcing**: 위반 차단 + 로그 기록
- **Permissive**: 위반 허용 + 로그만 기록 (튜닝 시 유용)
- **Disabled**: 완전 비활성 (권장하지 않음)

### 보안 컨텍스트

```bash
ls -Z /var/www/html/index.html
# 출력: unconfined_u:object_r:httpd_sys_content_t:s0
```
형식: `user:role:type:level`
- `type`이 가장 중요 (예: `httpd_t` 프로세스, `httpd_sys_content_t` 파일)

### Boolean (스위치)

```bash
getsebool -a | grep httpd
setsebool -P httpd_can_network_connect on   # 영구 적용
```
Boolean은 미리 정의된 허용/차단 스위치다.

## 파일·포트 라벨링

### 파일 컨텍스트 (영구 규칙)

```bash
# 규칙 추가
sudo semanage fcontext -a -t httpd_sys_content_t '/srv/www(/.*)?'
# 적용
sudo restorecon -Rv /srv/www
```

일시적 변경은 `chcon`을 사용하지만, `restorecon` 시 원래대로 돌아가므로 권장되지 않는다.

### 포트 컨텍스트

```bash
sudo semanage port -a -t http_port_t -p tcp 8081
sudo semanage port -l | grep http_port_t
```

## SELinux 로그 해석과 문제 해결

### 로그 확인

```bash
sudo ausearch -m avc -ts recent          # 최근 차단 이벤트
sudo journalctl -t setroubleshoot        # 도움말
```

### 원인 분석

```bash
sudo cat /var/log/audit/audit.log | audit2why
```

출력은 보통 세 가지 원인을 알려준다:
- 잘못된 파일/포트 라벨
- Boolean 비활성화
- 정책 모듈 누락

### 최소 허용 정책 생성 (정말 필요할 때)

```bash
# audit 로그 기반 정책 생성
sudo grep denied /var/log/audit/audit.log | audit2allow -M my_policy
sudo semodule -i my_policy.pp
```

> **원칙**: Boolean이나 라벨링으로 해결 가능한지 먼저 확인하고, 정책 모듈은 최소화한다.

## 서비스별 SELinux 튜닝 예시

### 웹 서버 (NGINX/Apache)

```bash
# 웹 루트 변경
sudo semanage fcontext -a -t httpd_sys_content_t '/srv/www(/.*)?'
sudo restorecon -Rv /srv/www

# 외부 네트워크 연결 허용 (API 호출 등)
sudo setsebool -P httpd_can_network_connect on
```

### 데이터베이스 (MariaDB) 디렉토리 이동

```bash
sudo semanage fcontext -a -t mysqld_db_t '/data/mysql(/.*)?'
sudo restorecon -Rv /data/mysql
```

### 컨테이너 볼륨 마운트 (podman/docker)

```bash
podman run -v /data/app:/app:Z -p 8080:8080 myimage
# :Z (private) 또는 :z (shared) 옵션으로 라벨 자동 조정
```

## SELinux 트러블슈팅 체크리스트

1. `getenforce`, `sestatus`로 상태 확인
2. `ausearch -m avc -ts recent`로 차단 로그 확인
3. 접근 대상의 라벨 확인 (`ls -Z`, `ps -eZ`)
4. 필요하면 라벨 보정: `semanage fcontext` → `restorecon`
5. Boolean 검토: `getsebool -a | grep <서비스>`
6. 정말 필요한 경우 `audit2allow`로 정책 생성
7. 재부팅 후에도 문제 없도록 테스트

## AppArmor: 경로 기반 프로파일

### 상태 및 프로파일 관리

```bash
aa-status                          # 전체 요약
sudo aa-enforce /etc/apparmor.d/usr.sbin.nginx
sudo aa-complain /etc/apparmor.d/usr.sbin.nginx   # 허용 + 로그
```

- **enforce**: 차단
- **complain**: 허용, 로그만 기록 (튜닝용)

### 프로파일 파일 예시

`/etc/apparmor.d/usr.bin.curl`:

```text
#include <tunables/global>

/usr/bin/curl {
  /etc/resolv.conf r,
  /etc/ssl/** r,
  network inet stream,
  network inet6 stream,
  deny /etc/shadow r,
}
```

### 로그 기반 보정 (aa-logprof)

```bash
sudo aa-logprof
# 로그에서 거부 이벤트를 읽고 대화형으로 허용/거부 결정 → 프로파일 자동 갱신
```

### 빠른 프로파일 생성

```bash
sudo aa-genprof /usr/sbin/mydaemon
# 데몬을 실행하며 접근 패턴 학습 → 초안 생성
```

## SELinux vs AppArmor 비교

| 항목 | SELinux | AppArmor |
|------|---------|----------|
| 정책 모델 | 라벨 기반 (Type Enforcement) | 경로 기반 프로파일 |
| 학습 난이도 | 높음 | 낮음 (직관적) |
| 주요 배포판 | RHEL, Fedora, Alma, Rocky | Ubuntu, Debian |
| 컨테이너 연동 | 매우 강력 (라벨 기반) | 무난 (경로/네임스페이스) |
| 튜닝 도구 | `semanage`, `restorecon`, `audit2allow` | `aa-logprof`, `aa-genprof` |

**실무 권장**:
- RHEL 계열 → SELinux 고수준 활용
- Ubuntu/Debian → AppArmor로 시작, 필요 시 SELinux 전환 검토

## 실전 예제

### SELinux: NGINX가 `/opt/site`와 8443 포트 사용

```bash
# 파일 라벨
sudo semanage fcontext -a -t httpd_sys_content_t '/opt/site(/.*)?'
sudo restorecon -Rv /opt/site

# 포트 라벨
sudo semanage port -a -t http_port_t -p tcp 8443

# 외부 연결 허용 (필요 시)
sudo setsebool -P httpd_can_network_connect on
```

### AppArmor: `/usr/local/bin/api` 감싸기

```bash
# 프로파일 생성 (complain 모드)
sudo aa-genprof /usr/local/bin/api

# 실제 기능 실행 → 로그 축적
# 로그 기반 보정
sudo aa-logprof

# 강제 모드로 전환
sudo aa-enforce /etc/apparmor.d/usr.local.bin.api
```

## 자주 쓰는 명령 요약

### SELinux

| 작업 | 명령 |
|------|------|
| 상태 | `getenforce`, `sestatus` |
| 임시 모드 전환 | `setenforce 0|1` |
| 파일 라벨 확인 | `ls -Z` |
| 파일 라벨 영구 설정 | `semanage fcontext -a -t type '/경로(/.*)?'` |
| 라벨 적용 | `restorecon -Rv 경로` |
| 포트 라벨 | `semanage port -a -t type -p tcp 포트` |
| boolean 확인/설정 | `getsebool -a`, `setsebool -P bool on` |
| 로그 분석 | `ausearch -m avc`, `audit2why` |
| 정책 모듈 생성 | `audit2allow -M 모듈명`, `semodule -i` |

### AppArmor

| 작업 | 명령 |
|------|------|
| 상태 | `aa-status` |
| 프로파일 강제/불평 | `aa-enforce 프로파일`, `aa-complain 프로파일` |
| 프로파일 생성 | `aa-genprof 실행파일` |
| 로그 기반 보정 | `aa-logprof` |
| 프로파일 파싱 적용 | `apparmor_parser -r /etc/apparmor.d/프로파일` |

## 결론

SELinux와 AppArmor는 리눅스 시스템 보안을 강화하는 MAC 기술이다.  
- **SELinux**는 강력하지만 다소 복잡하며, RHEL 계열에 적합하다.  
- **AppArmor**는 경로 기반으로 직관적이며, Ubuntu/Debian에 자연스럽게 통합된다.

운영에서 문제가 발생했을 때, 먼저 **로그(`ausearch`, `aa-logprof`)**를 확인하고, 대부분의 경우 **라벨 보정(SELinux)**이나 **프로파일 보정(AppArmor)**으로 해결할 수 있다. Boolean이나 경로 제한으로도 충분할 때가 많다.

보안 정책은 **최소 권한 원칙**으로 설계하고, **Permissive/complain 모드로 테스트**한 후 **Enforcing으로 전환**하는 단계를 거친다. 정기적인 로그 분석과 튜닝으로 시스템의 안정성과 보안성을 함께 유지할 수 있다.
