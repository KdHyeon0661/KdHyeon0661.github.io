# 데몬과 백그라운드 실행 관리

## 상황에 맞는 도구 선택

리눅스에서 장기 실행 프로세스(데몬)를 관리하는 방법은 다양하다.  
각 상황에 적합한 도구를 선택하는 것이 효율적인 운영의 첫걸음이다.

| 사용 시나리오 | 권장 도구 | 특징 |
|---|---|---|
| 빠른 테스트, 단발성 작업 | `nohup … &`, `disown`, `tmux` | 간편하지만 운영 기능 부족 |
| 운영 서비스 배포 | **`systemd` 서비스 유닛** | 자동 시작, 복구, 로깅, 보안 통합 |
| 요청 시 실행 | `systemd` 소켓 유닛 | 리소스 절약, 지연 실행 |
| 정기 작업 | `systemd` 타이머 유닛 | cron 대체, 통합 로깅 |
| 구형 시스템 | SysVinit (`/etc/init.d`) | 호환용, 가능하면 systemd로 이전 |

---

## 빠른 시작: 간단한 백그라운드 실행

### nohup과 disown
터미널 세션과 분리하여 프로세스를 유지하는 가장 간단한 방법이다.

```bash
nohup ./myapp > myapp.out 2>&1 &
disown
```
- `nohup` : SIGHUP(터미널 종료 신호) 무시
- `&` : 백그라운드 실행
- `disown` : 셸의 작업 목록에서 제거

### setsid
새로운 세션에서 프로세스를 시작한다.

```bash
setsid ./myapp > myapp.out 2>&1 < /dev/null &
```

**장점**: 설정이 빠르고 간단하다.  
**단점**: 자동 재시작, 로그 관리, 리소스 제한 등 운영에 필요한 기능이 없다.

---

## 세션 관리 도구: tmux

터미널 세션을 유지하며 여러 창을 관리할 수 있다.

```bash
# 새 세션 생성
tmux new -s app

# 세션 분리 (Ctrl+b, d)
# 세션 재연결
tmux attach -t app
```

스크립트로 자동화할 수도 있다.

```bash
# 세션이 없으면 생성하여 실행
tmux has-session -t app 2>/dev/null || tmux new -d -s app "./myapp"
```

**장점**: SSH 연결이 끊겨도 프로세스 유지, 다중 창 관리 용이.  
**단점**: 서비스 자동 복구, 운영 모니터링 기능 부족.

## 표준 솔루션: systemd 서비스

운영 환경에서 가장 권장되는 방식이다. systemd는 서비스의 시작/중지/재시작, 로깅, 의존성, 보안, 리소스 제한을 통합 관리한다.

### 서비스 유닛 파일 작성
`/etc/systemd/system/myapp.service`:

```ini
[Unit]
Description=MyApp HTTP Service
After=network.target

[Service]
Type=simple
User=myapp
Group=myapp
WorkingDirectory=/opt/myapp
ExecStart=/opt/myapp/myapp --port=8080
Restart=on-failure
RestartSec=3s

[Install]
WantedBy=multi-user.target
```

### 서비스 등록 및 관리

```bash
sudo systemctl daemon-reload            # 유닛 파일 변경 적용
sudo systemctl enable --now myapp       # 부팅 시 자동 시작 + 즉시 시작
sudo systemctl status myapp -l          # 상태 확인
journalctl -u myapp -f                  # 로그 실시간 보기
```

### 서비스 제어 명령

```bash
sudo systemctl start myapp
sudo systemctl stop myapp
sudo systemctl restart myapp
sudo systemctl reload myapp   # 설정 재로드 (서비스가 지원해야 함)
```

## 고급 systemd 기능 (핵심만)

### 재시작 정책과 제한

```ini
[Service]
Restart=on-failure           # on-failure / always / no
RestartSec=5s
StartLimitIntervalSec=30s
StartLimitBurst=10           # 30초 내 10회 실패 시 비활성화
```

### 리소스 제한

```ini
[Service]
LimitNOFILE=65535            # 열 수 있는 파일 수
MemoryMax=2G                 # 최대 메모리
CPUQuota=200%                # CPU 코어 2개 분량
TasksMax=4096                # 최대 프로세스/스레드 수
```

### 보안 강화 (최소 권한 원칙)

```ini
[Service]
User=myapp
Group=myapp
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
```

### 디렉터리 자동 관리

```ini
[Service]
StateDirectory=myapp         # /var/lib/myapp
LogsDirectory=myapp          # /var/log/myapp
RuntimeDirectory=myapp       # /run/myapp
```

## 소켓 활성화: 요청 시에만 실행

서비스를 항상 띄워두지 않고, 연결 요청이 있을 때만 시작한다.

**소켓 유닛** (`/etc/systemd/system/myapp.socket`):

```ini
[Unit]
Description=MyApp Socket

[Socket]
ListenStream=0.0.0.0:9090

[Install]
WantedBy=sockets.target
```

**서비스 유닛** (`/etc/systemd/system/myapp.service`):

```ini
[Unit]
Description=MyApp (socket-activated)
Requires=myapp.socket

[Service]
ExecStart=/opt/myapp/myapp
```

```bash
sudo systemctl enable --now myapp.socket
```

---

## 타이머 유닛: cron 대체

주기적 작업을 systemd로 관리한다.

**서비스 유닛** (`/etc/systemd/system/cleanup.service`):

```ini
[Unit]
Description=Nightly cleanup

[Service]
Type=oneshot
ExecStart=/usr/local/bin/cleanup.sh
```

**타이머 유닛** (`/etc/systemd/system/cleanup.timer`):

```ini
[Unit]
Description=Nightly cleanup timer

[Timer]
OnCalendar=*-*-* 03:00:00
Persistent=true
RandomizedDelaySec=5m

[Install]
WantedBy=timers.target
```

```bash
sudo systemctl enable --now cleanup.timer
systemctl list-timers
```

## 사용자 서비스

사용자별로 서비스를 실행할 수 있다. 파일은 `~/.config/systemd/user/`에 저장한다.

```bash
systemctl --user enable --now myapp
journalctl --user -u myapp -f
```

로그아웃 후에도 계속 실행하려면 `linger`를 활성화한다.

```bash
sudo loginctl enable-linger username
```

## 트러블슈팅 기본

### 서비스가 바로 종료될 때

```bash
systemctl status myapp -l
journalctl -u myapp -b | tail -30
```

### 포트 바인딩 권한 부족

1024 미만 포트를 루트 없이 사용하려면 capabilities를 추가한다.

```ini
[Service]
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
AmbientCapabilities=CAP_NET_BIND_SERVICE
```

### 파일 핸들 부족

```ini
[Service]
LimitNOFILE=65535
```

### 디렉터리 권한 문제

- `WorkingDirectory`가 존재하고 실행 사용자가 접근 가능한지 확인
- `StateDirectory`, `LogsDirectory` 등을 이용하면 자동 생성 및 권한 설정

## 핵심 명령어 요약

| 작업 | 명령어 / 파일 |
|------|----------------|
| 간단 백그라운드 실행 | `nohup cmd &`, `setsid cmd` |
| tmux 세션 관리 | `tmux new -s name`, `tmux attach -t name` |
| systemd 서비스 등록 | `/etc/systemd/system/서비스명.service` |
| 서비스 활성화/시작 | `sudo systemctl enable --now 서비스` |
| 서비스 상태 | `sudo systemctl status 서비스` |
| 서비스 로그 | `journalctl -u 서비스 -f` |
| 리소스 제한 | `LimitNOFILE=`, `MemoryMax=`, `CPUQuota=` |
| 사용자 서비스 | `systemctl --user ...` |
| linger 활성화 | `sudo loginctl enable-linger 사용자` |
| 소켓 활성화 | `.socket` 유닛 + `systemctl enable --now` |
| 타이머 유닛 | `.timer` 유닛 + `systemctl enable --now` |

## 결론

리눅스에서 데몬과 백그라운드 프로세스를 관리하는 방법은 다양하지만, 운영 환경에서는 **systemd 서비스 유닛**이 가장 강력하고 표준적인 방법이다.

- 빠른 테스트나 개인 작업에는 `nohup`이나 `tmux`로 충분하다.
- 정식 서비스는 systemd로 작성하여 자동 시작, 자동 복구, 로깅, 리소스 제한, 보안 강화를 체계적으로 적용한다.
- 소켓 활성화와 타이머 유닛을 활용하면 더 효율적인 시스템 운영이 가능하다.
- 사용자 서비스와 linger를 통해 일반 사용자도 자신의 서비스를 관리할 수 있다.

처음에는 `systemctl` 기본 명령과 간단한 서비스 유닛 작성부터 익히고, 점차 리소스 제한, 보안 설정, 소켓/타이머 등으로 확장하면 복잡한 서비스 환경도 안정적으로 운영할 수 있다.
