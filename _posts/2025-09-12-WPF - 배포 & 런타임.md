# WPF 배포 및 런타임 전략 완전 가이드

이 글에서는 WPF 애플리케이션을 실전에 배포하기 위한 핵심 전략을 소개합니다. **ClickOnce 배포**, **.NET 5 이상에서의 WPF 개발**, 그리고 **단일 실행 파일(Single‑file) 및 Self‑contained 배포** 방식을 중심으로, Visual Studio와 `dotnet` CLI 사용법, 프로젝트 파일 설정, 서명, 업데이트, 런타임 식별자(RID), 트리밍, ReadyToRun, ARM64 지원까지 다룹니다. 초중급 개발자도 쉽게 따라 할 수 있도록 핵심만 정리했습니다.

---

## 배포 전략 개요: 주요 선택지 비교

| 방식 | 장점 | 적합한 상황 |
|------|------|-------------|
| **ClickOnce** | 자동 업데이트, 증분 배포, 관리자 권한 없이 사용자 설치, 롤백 용이 | 웹 서버/파일 공유로 배포하고 자동 업데이트가 필요한 엔터프라이즈 앱 |
| **MSI / MSIX** | 복잡한 설치 작업(레지스트리, 서비스, 드라이버) 가능 / 현대적 패키징, 샌드박싱 | 전통적 설치 관리자 필요 시 / Microsoft Store 또는 사내 배포 |
| **Single‑file + Self‑contained** | .NET 런타임 포함, 대상 PC에 별도 설치 불필요, 이식성 높음 | USB 실행, 즉시 사용 배포, 런타임 설치가 어려운 환경 |

이 가이드는 **ClickOnce**와 **Self‑contained / Single‑file**에 집중하며, .NET 5 이상에서 WPF를 개발하기 위한 필수 설정도 함께 설명합니다.

## .NET 5 이상에서의 WPF 개발

### 프로젝트 기본 구성
```xml
<Project Sdk="Microsoft.NET.Sdk.WindowsDesktop">
  <PropertyGroup>
    <OutputType>WinExe</OutputType>
    <TargetFramework>net8.0-windows</TargetFramework>
    <UseWPF>true</UseWPF>
  </PropertyGroup>
</Project>
```

- `Microsoft.NET.Sdk.WindowsDesktop` SDK에 WPF와 WinForms가 포함됩니다.
- 필요 시 최소 OS 버전을 지정할 수 있습니다. 예: `net8.0-windows10.0.19041.0`

### 플랫폼 대상 (RuntimeIdentifier, RID)
Self‑contained 또는 단일 파일 배포 시 RID 지정이 필수입니다.
```xml
<PropertyGroup>
  <RuntimeIdentifier>win-x64</RuntimeIdentifier>  <!-- win-x86, win-arm64 등 -->
</PropertyGroup>
```
- 여러 아키텍처를 한 번에 빌드하려면 `RuntimeIdentifiers` 속성을 사용합니다.

### .NET 5 이상 WPF의 주요 이점
- 최신 C# 및 런타임 성능 향상
- ReadyToRun(사전 컴파일) 지원 → 시작 속도 개선
- Single‑file / Self‑contained 배포 완전 지원

**참고**: WPF는 현재 NativeAOT 대상이 아닙니다. JIT, 리플렉션, COM 상호 운용에 의존하므로 `PublishTrimmed=true`는 일반적으로 권장하지 않습니다.

## ClickOnce 배포

### ClickOnce를 선택하는 시나리오
- 관리자 권한 없이 사용자 단위 설치가 필요한 경우
- 웹 서버 또는 파일 공유를 통해 자동 업데이트를 제공하려는 경우
- 사내망에서 간편하게 배포하고 유지보수하고자 하는 경우

### Visual Studio를 이용한 ClickOnce 설정 (요약)
1. 프로젝트 속성 → **게시(Publish)** → ClickOnce 선택
2. 설치 모드: 온라인 전용 vs 오프라인 가능(바탕화면/시작 메뉴 설치)
3. 게시 위치: 웹 서버(HTTP/HTTPS), 파일 공유(SMB/UNC), 또는 로컬 폴더
4. 자동 업데이트 설정: 앱 시작 시 확인 여부, 업데이트 URL
5. 서명(Signing): 배포 매니페스트에 인증서 서명 및 타임스탬프 서버 지정
6. 필수 구성 요소: Framework‑dependent 배포 시 대상 PC에 .NET Desktop Runtime 필요

### .NET 5+ 프로젝트에서 ClickOnce 설정 (csproj / CLI)
```xml
<PropertyGroup>
  <TargetFramework>net8.0-windows</TargetFramework>
  <UseWPF>true</UseWPF>

  <!-- ClickOnce 관련 -->
  <GenerateManifests>true</GenerateManifests>
  <PublishProtocol>ClickOnce</PublishProtocol>
  <PublishDir>.\publish\clickonce\</PublishDir>
  <Install>true</Install>
  <CreateDesktopShortcut>true</CreateDesktopShortcut>
  <PublisherName>내 회사</PublisherName>
  <ProductName>내 WPF 앱</ProductName>
  <ApplicationRevision>1</ApplicationRevision>
  <ApplicationVersion>1.0.0.*</ApplicationVersion>   <!-- *: 빌드 시 자동 증가 -->
  <UpdateEnabled>true</UpdateEnabled>
  <UpdateMode>Foreground</UpdateMode>
  <UpdateInterval>1</UpdateInterval>
  <UpdateIntervalUnits>Days</UpdateIntervalUnits>
  <UpdateUrl>https://인트라넷.예제.com/app/</UpdateUrl>
</PropertyGroup>
```

CLI로 게시:
```bash
dotnet publish -c Release /p:PublishProfile=ClickOnceProfile
# 또는 csproj 속성 기반
dotnet publish -c Release
```

### 서명(Signing)
- **배포 매니페스트**는 반드시 인증서로 서명해야 합니다. 개발 시 자체 서명, 운영 환경에서는 공인 코드 서명 인증서를 사용합니다.
- **타임스탬프 서버**를 지정하면 인증서 만료 후에도 서명의 유효성을 유지할 수 있습니다.

```xml
<PropertyGroup>
  <ManifestCertificateThumbprint>0011223344AABBCCDDEEFF...</ManifestCertificateThumbprint>
  <ManifestTimestampUrl>http://timestamp.digicert.com</ManifestTimestampUrl>
</PropertyGroup>
```

### 데이터 및 설정 파일 관리
ClickOnce는 애플리케이션 파일을 읽기 전용 캐시에 저장하므로, 사용자 데이터는 별도 위치에 저장해야 업데이트 시 덮어쓰지 않습니다.
```csharp
if (ApplicationDeployment.IsNetworkDeployed)
{
    var dataDir = ApplicationDeployment.CurrentDeployment.DataDirectory;
    // dataDir 아래에 설정 파일 저장
}
```

### 일반적인 문제 해결

| 문제 | 원인 | 해결 |
|------|------|------|
| 설치/업데이트 시 신뢰 경고 | 서명 인증서 불신, 게시 URL 신뢰 부족 | 공인 인증서 사용, 타임스탬프 서버 설정, 사내 도메인 등록 |
| “구성 요소 없음(.NET)” 오류 | Framework‑dependent인데 대상 PC에 런타임 없음 | Self‑contained로 배포하거나 런타임 사전 설치 |
| 업데이트 후 사용자 설정 초기화 | 설정 파일이 앱 폴더에 저장됨 | `DataDirectory` 또는 `AppData` 폴더에 저장 |
| 웹 서버 배포 후 404 | MIME 타입 미설정, 파일 누락 | `.application` 및 `.manifest` 파일에 `application/x-ms-application` MIME 등록 |

## 단일 실행 파일(Single‑file) 및 Self‑contained 배포

### 개념
- **Self‑contained**: .NET 런타임을 애플리케이션에 포함 → 대상 PC에 별도 설치 불필요
- **Single‑file**: 모든 출력을 하나의 EXE 파일로 압축 (.NET 6 이상에서는 실행 시 임시 폴더에 압축 해제)
- **Framework‑dependent (FDD)**: 대상 PC에 .NET 런타임 필요 (패키지 크기 작음)

### 권장 설정 (csproj)
```xml
<Project Sdk="Microsoft.NET.Sdk.WindowsDesktop">
  <PropertyGroup>
    <OutputType>WinExe</OutputType>
    <TargetFramework>net8.0-windows</TargetFramework>
    <UseWPF>true</UseWPF>

    <!-- Self-contained: 런타임 포함 -->
    <SelfContained>true</SelfContained>
    <RuntimeIdentifier>win-x64</RuntimeIdentifier>

    <!-- Single-file: 단일 실행 파일 -->
    <PublishSingleFile>true</PublishSingleFile>
    <IncludeAllContentForSelfExtract>true</IncludeAllContentForSelfExtract>
    <EnableCompressionInSingleFile>true</EnableCompressionInSingleFile>

    <!-- (선택) ReadyToRun: 시작 성능 개선 (파일 크기 증가) -->
    <PublishReadyToRun>true</PublishReadyToRun>

    <!-- (주의) 트리밍: WPF는 리플렉션 의존도가 높아 false 권장 -->
    <PublishTrimmed>false</PublishTrimmed>
  </PropertyGroup>
</Project>
```

### CLI를 이용한 게시
```bash
dotnet publish -c Release -r win-x64 --self-contained true /p:PublishSingleFile=true
# ReadyToRun 포함
dotnet publish -c Release -r win-x64 --self-contained true /p:PublishSingleFile=true /p:PublishReadyToRun=true
```

### 제약사항 및 고려사항
- 네이티브/COM DLL은 외부 파일로 남을 수 있습니다.
- 실행 시 임시 폴더에 파일이 압축 해제되므로 `AppContext.BaseDirectory`를 사용해 경로를 얻으세요.
- 보안 소프트웨어(백신)가 압축 해제 과정을 검사하여 시작 속도에 영향을 줄 수 있습니다.
- 첫 실행이 느리다면 `PublishReadyToRun=true`로 개선 가능합니다.

### 다중 아키텍처 빌드
```bash
dotnet publish -c Release -r win-x64 --self-contained true /p:PublishSingleFile=true
dotnet publish -c Release -r win-arm64 --self-contained true /p:PublishSingleFile=true
```
출력 폴더를 구분하여 배포 파이프라인에서 사용자 플랫폼을 감지하도록 구성합니다.

## 실전 배포 구성 예시

### 시나리오 1: ClickOnce (Framework‑dependent, 작은 크기)
```xml
<PropertyGroup>
  <TargetFramework>net8.0-windows</TargetFramework>
  <UseWPF>true</UseWPF>
  <PublishProtocol>ClickOnce</PublishProtocol>
  <GenerateManifests>true</GenerateManifests>
  <Install>true</Install>
  <UpdateEnabled>true</UpdateEnabled>
  <UpdateUrl>https://deploy.mycorp.local/myapp/</UpdateUrl>
  <SelfContained>false</SelfContained>
</PropertyGroup>
```

### 시나리오 2: ClickOnce (Self‑contained, 런타임 포함)
```xml
<PropertyGroup>
  <PublishProtocol>ClickOnce</PublishProtocol>
  <GenerateManifests>true</GenerateManifests>
  <Install>true</Install>
  <UpdateEnabled>true</UpdateEnabled>
  <UpdateUrl>https://deploy.mycorp.local/myapp/</UpdateUrl>
  <SelfContained>true</SelfContained>
  <RuntimeIdentifier>win-x64</RuntimeIdentifier>
  <PublishSingleFile>false</PublishSingleFile>
</PropertyGroup>
```

### 시나리오 3: 단일 실행 파일 (Self‑contained, ClickOnce 미사용)
```xml
<PropertyGroup>
  <SelfContained>true</SelfContained>
  <RuntimeIdentifier>win-x64</RuntimeIdentifier>
  <PublishSingleFile>true</PublishSingleFile>
  <EnableCompressionInSingleFile>true</EnableCompressionInSingleFile>
  <PublishReadyToRun>true</PublishReadyToRun>
  <PublishTrimmed>false</PublishTrimmed>
</PropertyGroup>
```

## 보안 및 신뢰 관리
- **코드 서명(Authenticode)**: 실행 파일에 서명하면 Windows SmartScreen, 백신, 엔드포인트 보안 솔루션의 신뢰도를 높입니다.
- **ClickOnce 서명**: 배포 매니페스트 서명 필수.
- **사내 정책**: Active Directory 그룹 정책으로 신뢰할 수 있는 게시자 등록 가능.
- **타임스탬프**: 인증서 만료 후에도 유효성 유지.

## 업데이트 전략 비교
| 방식 | 업데이트 방법 |
|------|---------------|
| **ClickOnce** | 앱 시작 시 자동 확인, 증분 업데이트 및 롤백 내장 |
| **Single‑file (자체 구현)** | 앱 내에서 업데이트 서버 폴링, 새 버전 다운로드 후 교체 (별도 업데이터 프로세스 권장) |

## WPF 특화 고려사항 (.NET 5+)
- **High DPI**: `app.manifest`에 `PerMonitorV2` DPI 인식 모드 선언.
- **네이티브/COM 의존성**: P/Invoke 호출 DLL은 프로젝트에서 `CopyToOutputDirectory` 설정.
- **파일 경로**: 단일 파일 배포 시 리소스 접근은 `AppContext.BaseDirectory` 사용.
- **ReadyToRun**: 시작 성능 향상, 파일 크기 증가.

## 자주 묻는 질문 (FAQ) 및 문제 해결

**Q1. 단일 파일로 게시했는데 실행 파일 옆에 여러 파일이 생성됩니다.**  
A: 네이티브 라이브러리, COM 구성 요소 등은 외부로 남을 수 있습니다. `IncludeAllContentForSelfExtract=true`를 설정해도 완전히 단일 파일화되지 않을 수 있습니다.

**Q2. Single‑file 앱의 첫 실행이 매우 느립니다.**  
A: `PublishReadyToRun=true`로 시작 속도를 개선해 보세요. 또한 압축 해제 오버헤드로 인해 느려질 수 있으며, 백신 소프트웨어의 실시간 검사 영향도 있습니다.

**Q3. WPF 앱에 트리밍(PublishTrimmed)을 적용해도 안전한가요?**  
A: **일반적으로 권장하지 않습니다.** WPF는 데이터 바인딩, 리소스 딕셔너리, XAML 파싱 등에서 광범위하게 리플렉션을 사용하므로, 트리밍 과정에서 필요한 코드가 잘려나가 런타임 오류가 발생할 위험이 큽니다.

**Q4. ClickOnce로 배포한 앱의 환경설정 파일이 업데이트될 때마다 초기화됩니다.**  
A: 설정 파일을 `ApplicationDeployment.CurrentDeployment.DataDirectory` 또는 `Environment.SpecialFolder.ApplicationData` 폴더에 저장하세요.

**Q5. ARM64 Windows 장치도 지원하고 싶습니다.**  
A: `-r win-arm64`로 별도 게시하고, 배포 UI에서 사용자가 자신의 아키텍처에 맞는 버전을 선택할 수 있도록 구성하세요.

## 결론: 배포 전략 선택 가이드

WPF 애플리케이션의 배포 전략은 조직의 인프라, 대상 사용자, 유지보수 요구사항에 따라 결정합니다.

1. **ClickOnce**는 사내 업무용 애플리케이션이나 현장 배포 시 자동 업데이트와 롤백이 중요한 경우 매우 효과적입니다. 관리자 권한 없이 사용자 설치가 가능합니다.

2. **.NET 5 이상의 WPF**는 최신 언어 기능과 성능 개선을 제공하면서 기존 XAML 생태계를 그대로 유지합니다. `WindowsDesktop SDK`로 쉽게 전환할 수 있습니다.

3. **Self‑contained + Single‑file**은 최대한의 이식성과 배포 단순성을 원할 때 강력한 옵션입니다. 런타임 설치가 불가능한 환경이나 USB 실행 같은 시나리오에 적합합니다. 단, 파일 크기 증가와 자체 업데이트 구현 필요성을 고려해야 합니다.

각 방식의 장단점을 이해하고 애플리케이션의 특성에 맞게 선택하면, 유지보수성과 사용자 경험을 모두 만족시키는 배포 환경을 구축할 수 있습니다.
