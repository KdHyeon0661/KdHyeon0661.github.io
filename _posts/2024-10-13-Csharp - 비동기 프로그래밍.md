# C# 비동기 프로그래밍

현대 애플리케이션은 네트워크 호출, 데이터베이스 쿼리, 파일 입출력과 같이 대기 시간이 긴 작업을 빈번하게 처리합니다. 이러한 작업을 동기적으로 처리하면 스레드가 작업이 끝날 때까지 아무 일도 못 하고 블로킹되어 애플리케이션의 성능과 응답성이 저하됩니다.

C#은 이 문제를 해결하기 위해 `async`와 `await` 키워드를 도입했습니다. 비동기 코드를 마치 동기 코드처럼 읽을 수 있게 하면서도 내부적으로는 효율적인 상태 머신으로 동작합니다. 이 글에서는 비동기의 핵심 개념, `Task`와 스레드의 차이, 실무에서 반드시 알아야 할 `ConfigureAwait(false)`와 데드락 방지까지 체계적으로 정리합니다.

---

## async / await 기본

`async` 키워드는 메서드 내부에서 `await`를 사용할 것임을 컴파일러에 알립니다. `await`는 작업이 완료될 때까지 현재 메서드의 실행을 중단하되, 호출자에게 제어권을 즉시 반환합니다. 작업이 완료되면 중단된 지점부터 실행을 재개합니다.

```csharp
public async Task<string> DownloadDataAsync(string url)
{
    using var client = new HttpClient();
    
    // await를 만나면 실행을 중단하고 호출자에게 제어권을 반환
    string content = await client.GetStringAsync(url);
    
    // 네트워크 작업이 완료되면 여기서부터 실행 재개
    return content;
}
```

비동기 메서드는 `Task` 또는 `Task<T>`를 반환합니다. `Task<T>`는 작업이 완료되면 결과를 제공한다는 의미의 약속(promise)입니다.

---

## await의 동작 원리

컴파일러는 `async` 메서드를 상태 머신(state machine)으로 변환합니다. `await`를 만나면 다음을 수행합니다.

1. 작업이 이미 완료되었는지 확인 → 완료되었다면 동기적으로 계속 실행
2. 완료되지 않았다면 메서드의 현재 상태(지역 변수 등)를 저장하고 호출자에게 제어권 반환
3. 작업 완료 시 저장된 상태를 복원하고 나머지 코드 실행

```text
[await 상태 머신 개요]

async 메서드 호출
        │
        ▼
   await 지점
        │
   ┌────┴────┐
   │ 작업 완료? │
   └────┬────┘
     완료  미완료
      │      │
      │      ▼
      │   상태 저장
      │   제어권 반환
      │      │
      │      ▼
      │   (호출자 계속 실행)
      │      │
      ▼      ▼
   작업 완료 → 상태 복원 → 나머지 실행
```

이 구조 덕분에 스레드는 I/O 대기 중에도 다른 작업을 처리할 수 있습니다.

## Task와 Thread의 차이

비동기 입문자가 가장 혼란스러워하는 부분이 “Task가 곧 스레드인가?”입니다. 답은 **아니오**입니다.

- **스레드(Thread)**: 운영체제가 관리하는 실제 실행 흐름입니다. 생성 비용이 비싸며, 블로킹되면 자원이 낭비됩니다.
- **태스크(Task)**: 미래에 완료될 작업에 대한 명세서입니다. CPU 작업을 백그라운드에서 실행할 때는 스레드 풀에서 스레드를 빌려 사용하지만, 네트워크 I/O 같은 작업은 스레드를 점유하지 않습니다.

### CPU 바운드 vs I/O 바운드

```csharp
// CPU 바운드 작업: 스레드가 실제로 계산을 수행
Task.Run(() => CalculateLargeNumbers());

// I/O 바운드 작업: 스레드가 대기하지 않고, 하드웨어가 완료 신호를 줌
await httpClient.GetStringAsync(url);
```

실무에서는 I/O 바운드 작업을 `Task.Run`으로 감싸지 않습니다. `HttpClient`, `SqlConnection` 등이 제공하는 비동기 메서드를 직접 `await`하면 스레드 점유 없이 효율적으로 처리됩니다.

---

## Task 사용법과 예외 처리

`Task`는 작업의 상태(진행 중, 완료, 취소, 오류)를 캡슐화합니다.

```csharp
// CPU 작업을 백그라운드로 실행
Task<int> compute = Task.Run(() => ComplexCalculation());

// 이미 완료된 결과를 Task로 반환 (인터페이스 구현 등에 유용)
Task<int> completed = Task.FromResult(42);

// 예외 처리
try
{
    int result = await compute;
}
catch (InvalidOperationException ex)
{
    Console.WriteLine($"연산 오류: {ex.Message}");
}
```

**절대 피해야 할 패턴**: `Task.Wait()` 또는 `Task.Result`를 사용해 비동기 코드를 동기적으로 블로킹하는 것입니다. 이는 스레드를 낭비할 뿐만 아니라 데드락의 주요 원인이 됩니다. 비동기 메서드는 호출 스택 전체에서 `await`로 이어져야 합니다.

### 작업 취소

`CancellationToken`을 사용하면 작업을 중단할 수 있습니다.

```csharp
public async Task ProcessAsync(CancellationToken token)
{
    // 토큰을 비동기 메서드에 전달
    var data = await FetchDataAsync(url, token);
    
    // 주기적으로 취소 요청 확인
    token.ThrowIfCancellationRequested();
    
    await SaveDataAsync(data, token);
}
```

## ConfigureAwait(false)와 SynchronizationContext

`await`로 실행을 재개할 때, 기본적으로 **원래의 동기화 컨텍스트(SynchronizationContext)** 로 돌아가려고 합니다. UI 애플리케이션(WPF, WinForms)에서는 UI 스레드, ASP.NET Classic에서는 요청 컨텍스트입니다. 이는 UI 컨트롤에 안전하게 접근하거나 요청 상태를 유지하기 위함입니다.

### 데드락 발생 시나리오

```csharp
// UI 버튼 클릭 (UI 스레드)
void Button_Click()
{
    // 🔴 위험: 비동기 메서드를 동기적으로 대기하면서 UI 스레드 블로킹
    var data = GetDataAsync().Result; 
}

async Task<string> GetDataAsync()
{
    // 작업이 끝나면 원래 컨텍스트(UI 스레드)로 돌아가려 함
    return await httpClient.GetStringAsync(url);
}
```

`Button_Click`이 UI 스레드를 점유한 채 `Result`를 기다리고, `GetDataAsync`는 UI 스레드가 비워지기를 기다리며 상호 데드락이 발생합니다.

### ConfigureAwait(false)의 역할

`ConfigureAwait(false)`는 컴파일러에게 “작업이 끝난 후 원래 컨텍스트로 돌아갈 필요 없이, 그냥 스레드 풀의 아무 스레드에서 나머지를 실행해도 된다”고 지시합니다.

```csharp
async Task<string> GetDataAsync()
{
    // 원래 컨텍스트로 돌아가지 않음 → 데드락 회피
    return await httpClient.GetStringAsync(url).ConfigureAwait(false);
}
```

```text
[ConfigureAwait(false) 동작]

await 호출
    │
    ▼
작업 완료
    │
    ├─ ConfigureAwait(true) : 원래 컨텍스트로 복귀 (UI 스레드)
    └─ ConfigureAwait(false): 스레드 풀의 아무 스레드에서 계속
```

### 실무 적용 규칙

- **공통 라이브러리(DLL)** : UI를 건드릴 일이 없으므로 `ConfigureAwait(false)`를 기본으로 사용하여 성능과 안정성을 높입니다.
- **UI 레이어 (버튼 클릭, 뷰모델)** : 결과를 화면에 반영해야 하므로 `ConfigureAwait(false)`를 사용하면 안 됩니다. UI 컨트롤은 UI 스레드에서만 조작 가능하기 때문입니다.

## 실전 예제: 견고한 비동기 서비스

아래는 앞서 설명한 모든 개념(비동기 I/O, 예외 처리, 취소 토큰, ConfigureAwait)을 적용한 서비스 클래스입니다.

```csharp
public class DownloadService
{
    private readonly HttpClient _httpClient;
    
    public DownloadService(HttpClient httpClient)
    {
        _httpClient = httpClient;
    }
    
    public async Task<string> DownloadContentAsync(string url, CancellationToken token = default)
    {
        try
        {
            // I/O 작업이므로 스레드 점유 없음
            // 공통 라이브러리이므로 ConfigureAwait(false) 사용
            using var response = await _httpClient.GetAsync(url, token)
                                                   .ConfigureAwait(false);
            response.EnsureSuccessStatusCode();
            
            return await response.Content.ReadAsStringAsync(token)
                                         .ConfigureAwait(false);
        }
        catch (OperationCanceledException)
        {
            // 취소는 상위로 전달
            throw;
        }
        catch (Exception ex)
        {
            // 의미 있는 예외로 래핑
            throw new DownloadException($"다운로드 실패: {url}", ex);
        }
    }
}

public class DownloadException : Exception
{
    public DownloadException(string message, Exception inner) : base(message, inner) { }
}
```

## 비동기 성능 고려 사항

비동기 코드는 성능이 무조건 빠른 것은 아닙니다. 작은 작업을 `async`로 감싸면 상태 머신 생성 비용이 오히려 오버헤드가 될 수 있습니다. 또한 `async void`는 예외 처리가 어렵고 호출자에게 작업 완료를 알릴 수 없으므로, 이벤트 핸들러를 제외하고는 사용하지 않는 것이 원칙입니다.

- `async void` → UI 이벤트 핸들러 이외에는 사용 금지
- `ValueTask<T>` → 자주 완료되는 비동기 작업에 사용 (힙 할당 최소화)

```csharp
// 이벤트 핸들러만 async void 허용
public async void Button_Click(object sender, EventArgs e)
{
    await LoadDataAsync();
}
```

## 마무리

C#의 `async/await`는 백그라운드 스레드를 쉽게 다루는 도구가 아니라, 한정된 스레드 자원을 효율적으로 사용하여 애플리케이션의 확장성과 응답성을 높이는 핵심 기술입니다.

- I/O 작업은 `Task.Run` 없이 직접 `await`합니다.
- 비동기 메서드는 호출 스택 전체를 `async/await`로 연결합니다(Async All the Way).
- `Task.Wait()`나 `Task.Result`는 사용하지 않습니다.
- 공통 라이브러리에서는 `ConfigureAwait(false)`를 습관화합니다.
- 취소 토큰을 통해 작업을 협력적으로 중단할 수 있도록 설계합니다.

이 원칙들을 따르면 응답성이 뛰어나고 대규모 동시 요청을 안정적으로 처리하는 애플리케이션을 구축할 수 있습니다.
