# 프로세스와 서비스 관리

## 프로세스란 무엇인가

프로세스는 실행 중인 프로그램의 인스턴스로, 운영체제로부터 고유한 식별자인 **PID**(Process ID)를 할당받는다. 각 프로세스는 독립적인 메모리 공간, 열린 파일 목록, 시그널 처리 방식, 그리고 하나 이상의 실행 스레드를 가진다.

프로세스는 보안과 자원 관리를 위한 속성을 함께 가진다. **UID/GID**는 프로세스를 실행한 사용자와 그룹을 나타내며, 파일 접근 권한을 결정하는 데 사용된다.

### 핵심 용어

* **PID / PPID** : 프로세스 고유 ID와 부모 프로세스 ID
* **UID / EUID** : 프로세스 소유자와 실제 파일 접근 시 사용되는 권한
* **GID / EGID** : 그룹에 대한 유사한 개념
* **TTY** : 프로세스가 연결된 터미널 장치 (데몬은 보통 `?`로 표시)
* **nice 값** : CPU 스케줄링 우선순위 (-20 ~ 19, 낮을수록 높은 우선순위)

## 프로세스 상태와 생명주기

`ps` 명령어로 확인할 수 있는 프로세스 상태는 실행 흐름을 이해하는 데 중요하다.

| 상태 | 의미 |
|------|------|
| **R (Running)** | CPU에서 실행 중이거나 실행 가능한 상태 |
| **S (Sleeping)** | 인터럽트 가능한 대기 상태 (I/O 이벤트 등 대기) |
| **D (Uninterruptible sleep)** | 인터럽트 불가능한 대기 상태 (주로 디스크 I/O) |
| **T (Stopped)** | 작업 제어 시그널에 의해 중지된 상태 |
| **Z (Zombie)** | 종료되었으나 부모가 상태를 회수하지 않은 상태 |

리눅스에서 새로운 프로세스는 `fork()` 시스템 호출로 생성되고, 이후 자식 프로세스는 `execve()`로 새로운 프로그램 이미지로 교체된다.

좀비 프로세스는 시스템 리소스를 거의 소모하지 않지만, 프로세스 테이블 슬롯을 점유한다.
```bash
ps -eo pid,ppid,stat,cmd | awk '$3 ~ /Z/ {print}'
```

## /proc 파일시스템: 프로세스 정보

`/proc`은 커널과 프로세스 정보를 파일 형태로 제공하는 가상 파일시스템이다. 각 프로세스는 `/proc/<PID>/` 디렉터리로 표현된다.

```bash
echo $$                              # 현재 쉘의 PID 확인
cat /proc/$$/environ | tr '\0' '\n'  # 환경변수 확인
cat /proc/$$/cmdline | tr '\0' ' '   # 명령줄 확인
ls -l /proc/$$/fd                    # 열린 파일 디스크립터 목록
```

## 프로세스 정보 조회 도구

### ps – 프로세스 스냅샷

```bash
ps aux          # BSD 스타일: 모든 사용자 상세 정보
ps -ef          # UNIX 스타일: 전체 포맷
ps -eo user,pid,ppid,stat,%cpu,%mem,cmd --forest  # 트리 형태
```

### top / htop – 실시간 모니터링

```bash
top
```

`top`에서 주요 인터랙티브 명령어:
* `P`: CPU 사용률 기준 정렬
* `M`: 메모리 사용률 기준 정렬
* `k`: 프로세스 종료
* `r`: nice 값 변경

`htop`은 `top`의 향상된 버전으로 컬러, 마우스 조작, 직관적인 트리 뷰를 제공한다.

### pstree – 프로세스 관계 트리

```bash
pstree -p        # PID 함께 표시
pstree -au       # 사용자와 명령어 인자까지
```

## 프로세스 검색과 제어

### pgrep / pidof – 이름으로 찾기

```bash
pgrep -a nginx                      # nginx 프로세스의 PID와 명령어
pgrep -u www-data nginx             # 특정 사용자가 실행한 프로세스
pidof sshd                          # 실행 파일 이름으로 PID 찾기
```

### kill / killall – 시그널 전송

```bash
kill 1234                           # 정상 종료 요청 (SIGTERM)
kill -9 1234                        # 강제 종료 (SIGKILL)
kill -HUP $(pidof nginx)            # 설정 재로드
killall -TERM myworker              # 이름으로 종료
```

주요 시그널:

| 시그널 | 번호 | 용도 |
|--------|------|------|
| SIGHUP | 1 | 터미널 연결 끊김, 데몬 설정 재로드 |
| SIGINT | 2 | Ctrl+C, 대화형 프로그램 종료 |
| SIGTERM | 15 | 정상 종료 요청 (기본) |
| SIGKILL | 9 | 강제 종료 (무시 불가) |
| SIGSTOP | 19 | 실행 중지 |
| SIGCONT | 18 | 중지된 프로세스 재개 |

안전한 종료 패턴:
```bash
kill -TERM $PID && sleep 5 && kill -0 $PID 2>/dev/null && kill -KILL $PID
```

## 프로세스 우선순위 조정

nice 값은 CPU 스케줄링 우선순위에 영향을 준다. 일반 사용자는 자신의 프로세스 우선순위를 낮출 수만 있고, 높이려면 `sudo`가 필요하다.

```bash
nice -n 10 ./cpu_intensive.sh   # 우선순위 낮게 실행
sudo renice -n -5 -p 1234       # 실행 중인 프로세스 우선순위 높이기
```

## 장기 실행 작업과 세션 관리

터미널 세션이 끊기면 해당 터미널에서 실행 중인 프로세스는 `SIGHUP`을 받고 종료된다. 이를 방지하는 방법:

```bash
./long_task.sh &                 # 백그라운드 실행
jobs                             # 작업 목록 확인
fg %1                            # 포그라운드로 가져오기
bg %1                            # 백그라운드 재개

nohup ./long_task.sh &           # 터미널 종료 후에도 실행 유지
disown -h %1                     # 셸의 작업 테이블에서 제거하고 HUP 무시
setsid ./server &                # 새로운 세션에서 시작
```

`tmux`나 `screen`을 사용하면 세션을 유지하고 재연결할 수 있어 가장 강력하다.
```bash
tmux new -s mysession            # 세션 생성
# 작업 후 Ctrl+b, d 로 분리
tmux attach -t mysession         # 재연결
```

## 프로세스 리소스 제한

### ulimit – 셸 및 프로세스 제한

```bash
ulimit -a                        # 모든 제한 확인
ulimit -n 1048576                # 최대 열 수 있는 파일 수
ulimit -u 4096                   # 사용자당 최대 프로세스 수
```

영구 설정은 `/etc/security/limits.conf` 또는 systemd 서비스 유닛의 `LimitNOFILE=` 등을 사용한다.

### cgroups (간략)

cgroups(control groups)는 프로세스 그룹 단위로 CPU, 메모리, I/O를 제한하는 커널 기능이다. systemd는 각 서비스 유닛을 cgroup으로 관리하며, 유닛 파일에서 리소스 제한을 설정할 수 있다.

## 서비스 관리: systemd

현대 리눅스 배포판은 시스템 및 서비스 관리자로 **systemd**를 사용한다.

### 기본 명령어

```bash
sudo systemctl start nginx       # 서비스 시작
sudo systemctl stop nginx        # 서비스 정지
sudo systemctl restart nginx     # 재시작
sudo systemctl reload nginx      # 설정만 재로드
sudo systemctl status nginx      # 상태 확인
sudo systemctl enable nginx      # 부팅 시 자동 시작 활성화
sudo systemctl disable nginx     # 비활성화
systemctl list-units --type=service --all
```

### journalctl – 로그 조회

systemd는 이진 저널에 로그를 저장하며, `journalctl`로 조회한다.

```bash
journalctl -u nginx              # nginx 서비스의 모든 로그
journalctl -u nginx --since "2025-11-10 09:00"
journalctl -u nginx -f           # 실시간 팔로우
journalctl -p err..emerg         # 오류 이상 로그만
journalctl -b -1                 # 직전 부팅 로그
```

## 실전: 커스텀 systemd 서비스 유닛 작성

서비스를 systemd로 관리하려면 서비스 유닛 파일(`.service`)을 `/etc/systemd/system/`에 작성한다.

### 간단한 Python HTTP 서버 예제

```ini
# /etc/systemd/system/hello-http.service
[Unit]
Description=Hello HTTP Server
After=network-online.target

[Service]
ExecStart=/usr/bin/python3 -m http.server 8080
WorkingDirectory=/srv/hello
User=www-data
Group=www-data
Restart=on-failure
RestartSec=2

[Install]
WantedBy=multi-user.target
```

파일 작성 후 적용 및 시작:

```bash
sudo mkdir -p /srv/hello
echo "Hello from systemd" | sudo tee /srv/hello/index.html
sudo systemctl daemon-reload
sudo systemctl enable --now hello-http.service
systemctl status hello-http
```

### 유닛 파일 수정과 오버라이드

기본 유닛 파일을 직접 수정하는 대신 오버라이드를 사용한다.

```bash
sudo systemctl edit hello-http
```

이 명령은 `/etc/systemd/system/hello-http.service.d/override.conf` 파일을 열어 수정할 수 있게 한다.

```ini
[Service]
ExecStart=/usr/bin/python3 -m http.server 9090
Environment=GREETING=annyeong
```

변경 후 `sudo systemctl daemon-reload`와 재시작이 필요하다.

## systemd 고급 구성 요소 (간략)

### 타이머 유닛: cron 대체

systemd 타이머는 더 정교한 스케줄링과 로깅을 제공한다.

서비스 유닛 (`/etc/systemd/system/backup.service`):
```ini
[Unit]
Description=Nightly Backup
[Service]
Type=oneshot
ExecStart=/usr/local/bin/backup.sh
```

타이머 유닛 (`/etc/systemd/system/backup.timer`):
```ini
[Unit]
Description=Nightly Backup Timer
[Timer]
OnCalendar=*-*-* 03:00:00
Persistent=true
[Install]
WantedBy=timers.target
```

```bash
sudo systemctl enable --now backup.timer
systemctl list-timers
```

### 타겟 (런레벨)

- `multi-user.target`: 텍스트 모드 다중 사용자 환경
- `graphical.target`: 그래픽 로그인 환경

```bash
systemctl get-default
sudo systemctl set-default multi-user.target
```

## cgroups를 이용한 리소스 제한 (간략)

systemd 서비스 유닛 파일에서 리소스 제한을 설정할 수 있다.

```ini
[Service]
CPUQuota=50%          # CPU 시간 50% 제한
MemoryMax=512M        # 최대 메모리 사용량
MemoryHigh=384M       # 소프트 제한
```

설정 적용 후 `systemd-cgtop`으로 cgroup별 리소스 사용량을 모니터링할 수 있다.

## 트러블슈팅 가이드라인

### 서비스가 시작되지 않을 때

```bash
systemctl status my.service
journalctl -u my.service -b --no-pager
journalctl -u my.service -r | head -20
```

### 포트 충돌

```bash
ss -tulpn | grep :8080
sudo lsof -i :8080
```

### 파일 권한, SELinux 문제

```bash
namei -l /path/to/file
ls -lZ /path/to/file
getenforce
sudo ausearch -m avc -ts recent
```

### CPU/메모리 과다 사용

```bash
top
sudo systemd-cgtop
sudo renice -n 10 -p <pid>
```

### 파일 디스크립터 부족

```bash
sudo ls -l /proc/<pid>/fd | wc -l
ulimit -n
cat /proc/sys/fs/file-max
```

## 결론

리눅스에서 프로세스와 서비스를 효과적으로 관리하는 능력은 시스템 운영의 기본이다. 이 문서는 프로세스의 기본 개념부터 상태 확인, 제어, 그리고 systemd를 통한 서비스 관리까지의 핵심 내용을 다루었다.

문제 해결 시에는 `ps`, `top`, `systemctl status`, `journalctl`을 이용해 체계적으로 접근하는 습관이 중요하다. 안정적인 서비스 운영을 위해 systemd 유닛 파일에 재시작 정책과 리소스 제한을 적절히 설정하는 것이 좋다.

처음에는 `htop`과 `journalctl -f`로 일상적인 모니터링을, 서비스 제어에는 `systemctl` 명령어를 익히는 것을 추천한다. 이를 바탕으로 점차 고급 주제로 확장해 나가면 복잡한 리눅스 시스템도 자신 있게 다룰 수 있을 것이다.
